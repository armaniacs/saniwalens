Docs

The design intent lives in docs/specs/; this page maps it to the commands you run. The README is how to run it; the specs are why.

Pipeline

Analyze once, read many times — the store decouples the stages
Command What it does
saniwalens doctor The health check, split global / per-project — start here.
saniwalens analyze Extract transcripts + config into the store (incremental). Reads run it automatically.
saniwalens sql '<query>' Arbitrary read-only SQL against the store. The store is the whole point.
saniwalens optimize Hand findings to an advisor session to act on.
saniwalens cleanup List or prune saved --apply plans and backups. Needs no store.

Views

Each is a curated lens that carries logic a raw query cannot (a classification, an algorithm, a suggestion). Scopes: --scope global | project | project:<slug>.

Spec map

  • architecture.md — two stages decoupled by SQLite; catalog × usage join
  • cli.md — command contract and reporting model (generated CLI reference)
  • surfaces.md — configuration-surface catalog
  • events.md — usage-event spine
  • storage.md — store schema and migration
  • harness.md — per-harness contract
  • session-format*.md — transcript formats per harness
  • config-format*.md — config formats per harness

Notes that save you a surprise

  • Counts are usage signals for ranking, not a billing ledger.
  • The store outlives your transcripts — deleting it is a real loss, not a cache flush.
  • The store migrates in place across schema changes; you never need to delete it.
  • Report tables stay English; --language en|ja switches only the advisor prompt.
