Architecture Specification

saniwalens answers one question about a coding-agent setup: **where can the

configuration be optimized, and how?** It does that by measuring, from real

usage, the cost and actual use of every configuration surface ― skills,

rules, hooks, MCP servers and their tool schemas, agents, CLAUDE.md /

AGENTS.md / memory, permissions ― and surfacing the wedges between the two.

Skills are one surface among many. The tool is configuration-wide. AI-assisted

optimization *proposals* are a planned later layer; the core measures and

visualizes, it does not advise.

The design follows from three facts about the problem:

  1. Two inputs, both upstream-owned. Cost and use cannot be read from one

source. *What is installed and what it costs* comes from live config

(skill/rule files, settings.json, MCP schemas); *what was actually used and

at what runtime cost* comes from session transcripts. Both formats are

Claude Code's, and both change between releases.

  1. The answer is a join, not a tally. Optimization opportunities live in the

gap between configured and used: installed-but-never-invoked, costly-but-rare,

redundant. So the model must relate a catalog of surfaces to a log of usage.

  1. Re-parsing is expensive; analysis is iterative. Hundreds of megabytes are

read once into a compact store; every report (and the future AI layer) reads

the store.

Two stages


flowchart LR


    raw["transcripts + config"] -->|analyze| db[("SQLite<br/>sessions ・ surfaces ・ events")]


    db -->|views / sql| out["CLI tables / Markdown"]


    db -->|optimize| ai["interactive claude session<br/>(AI optimization proposals)"]
  • **analyze** reads both inputs and writes the normalized store. The verb is

analyze (not build): the command *analyzes* raw input into facts, it does

not build an artifact.

  • The read commands ― the curated views and the arbitrary-query sql ―

query the store and render. See cli.md.

The stages are decoupled *only* by the store. The read commands' rendering

never reads raw input; analyze never renders. But the stages compose: a

view runs the incremental analyze stage first by default (cli.md

--frozen), the way optimize always has ― otherwise the store silently goes

stale and the user cannot notice. Composition is stage-before-stage, not a leak:

the view's queries still see only the store. Consumers read the same store. Two

were anticipated, and shape what analyze must capture:

  • Optimization proposals ― turning the findings into concrete advice. This

is realized by optimize (cli.md): it composes the headline findings with a

prescribed advisor prompt and hands them to an interactive claude session.

The prompt composition is a pure transform (core::optimize); only the process

launch is I/O. It reads aggregates; it needs nothing the store does not already

hold.

  • Skill extraction ― clustering recurring user prompts into candidate new

skills (the "synthesize a new surface" goal, distinct from pruning existing

ones). The store keeps only the pointer (events.prompt → `(source_path,

source_line); storage.md); the prompts` view re-reads the text at

report time, masks variable spans (quoted strings, paths, numbers) into a

reusable template (core::prompt), and lists templates repeated at least

three times as candidates with a count, an exemplar, and their sources.

Rotated or missing transcripts count as pruned, never as errors. Reworded

asks that no masking unifies stay unclustered ― that recall limit is

documented, not papered over. Proposals are presented only, never advised.

The central model: catalog × usage


flowchart TD


    cfg["config files"] -->|adapter| S["surfaces<br/>(catalog: what is installed + static cost)"]


    tx["transcripts"] -->|adapter| E["events<br/>(usage: what ran + runtime cost)"]


    S --> J["surface × usage join"]


    E --> J


    J --> W["optimization wedges<br/>(unused ・ costly+rare ・ redundant ・ friction)"]
  • A surface is one configurable thing (a skill, a rule, an MCP server, …)

with a static cost ― the token weight of its definition, measured by

reading the config file. See surfaces.md and config-format.md.

  • An event is one timestamped occurrence with a runtime cost (tokens,

context growth, duration). A skill invocation is one event kind among many.

See events.md and session-format.md.

  • A surface with no matching events is unused; a surface whose static cost is

high but whose events are few is a prune candidate. The join is the product.

Layers

Inside analyze, knowledge is stratified so an upstream format change lands in

exactly one layer.

    C -->|surfaces / events| S["store (SQLite)"]


    S --> R["report (store → presentation)"]

The view-landing rule (per PR)

The "next view" above is not left to memory. A PR that adds a Command variant

― a new view ― lands the view as one file under src/cli/views/:

  • **src/cli/views/ exists since the guided-entry PR.** It was created in

that same PR, which moved the trend view from directly under cli/ into

cli/views/ alongside the new cli/views/guide.rs. The "created when

the next view lands" deferral is discharged ― future views add one file

under cli/views/, nothing more.

  • View helpers are born in the view's file, never appended to

cli/mod.rs: the shell keeps dispatch, and nothing else.

  • The line-budget tripwire (tests/cli_mod_line_budget.rs) makes the

"never re-grow a shared file" half structural: growing cli/mod.rs past its

measured budget fails cargo test with a message pointing at cli/views/.

Raising the budget is a review point, done in the same PR as the spec

update it forces.

  • The spec update map when the split landed ― two places changed with it,

in the same PR: this rule, and the report row of the layer table above (it

names the current file layout). Both describe the landed src/cli/views/

instead of the future split.

The acceptance-criteria template every view-addition PBI carries is

.claude/rules/cli-view-addition.md.

The pure-join placement rule (per PR)

The core row's "shapes rows already fetched from the store" is not left to

memory either. A pure join ― a pairing, ordering, or delta over in-memory

values, no SQLite ― is core's wherever it is called from today

(.claude/rules/pure-join-placement.md):

  • A new pure join is born in core, with its tests there; the store keeps the

query and the row hand-off, never the shaping. The one integration test

pinning the query→join window split

(two_window_aggregation_splits_events_between_the_windows) stays in

store.rs with the query it tests.

  • The trend view's two-window joins (skill_deltas, TwoWindow,

SkillDelta, TrendWindowAggregates, kind_pairs) were the 1st pattern:

they predated the rule and sat in store.rs. PBI 46 fired the trend-metric

trigger (1ecda2a / 3b4349f) but the move did not ride that landing;

PBI 61 (2026-11-02) is the follow-up remediation that moved them to

src/core/trend.rs. The store keeps the windowed queries that hand them

rows; kind_pairs was the fifth join, found in the trend view only because

the move enumerated them. Trigger 2 (the next SQLite-free function) remains

armed for the next accumulation.

  • The trigger is grep-able, not a parser: the rule enumerates the symbols, and

tests/pure_join_placement.rs fails when the enumeration and core drift

apart. A join that leaves core or re-enters the store carries the core row

above, the rule's enumeration, the ledger's note, and the tripwire's move

side in the same PR.

The four points landed together with the move (PBI 61): the core row above,

the rule's enumeration, the ledger's deferral note, and the tripwire itself.

The tripwire's move side now asserts that the definitions sit in

src/core/trend.rs and no longer in store.rs; it turns red if one leaves

core or re-enters the store. The flip is not a follow-up: an emptied array

makes both sides of the tripwire pass vacuously, and a tombstone comment

satisfies a raw contains. Retiring the tripwire instead rewrites the two

prose anchors that name it (the rule and this section) in the same PR.

The contract between adapter and everything else is the **internal domain

model** ― tool-centric names stable across Claude Code releases. Renaming an

upstream field or moving a config file changes the adapter's mapping, nothing

downstream. This boundary is enforced by .claude/rules/format-isolation.md; a

format change whose diff escapes the adapter is a boundary bug.

The per-harness routine that walks this pipeline sits behind one seam:

Harness::analyze (adapter::harness) dispatches to each harness's own module

― adapter::claude, adapter::opencode, adapter::kilocode ― which owns that

harness's input route, fingerprinting, and extraction wiring, and hands rows to

Store::ingest (the store's API, never SQL). The analyzer-version key each

harness stamps lives beside its mapping, and the store compares whatever pair it

is handed. A new harness therefore adds a variant and a module; the shell does

not change (harness.md).

Why a pure core

The tool's value is its analysis logic ― event boundaries, the compaction-safe

context metric, subagent attribution, the catalog×usage join. That logic is

where bugs hide and where the specs make the most claims, so it must be

exhaustively unit-testable. Keeping it free of I/O, clocks, and SQL lets every

rule be driven by a small synthetic fixture (.claude/rules/tdd.md). File

walking, reading, tokenizing, SQLite, and "now" are thin shells; non-determinism

(current time, timezone, tuning constants) is injected.

Forward compatibility

The adapter deserializes defensively: it reads only the fields the tool needs,

ignores unknown fields, tolerates missing optional ones. A new Claude Code field

or config key must never break analyze. The concrete shapes the adapter

depends on ― and which are most likely to drift ― are catalogued in

session-format.md (transcripts) and config-format.md (config).

What this tool deliberately is not

  • Not a live monitor. It analyzes inputs at rest, not a running session.
  • Not a billing tool. Token counts rank surfaces; they are not an accounting

ledger. Approximations (estimated subagent attribution, tokenizer-based static

cost) are acceptable and flagged, not avoided.

  • Not an advisor (yet). The core reports opportunities; turning them into

concrete proposals is the future AI layer's job.

  • Not a data store. Raw transcripts and config stay where Claude Code put

them; the tool reads them read-only and never copies them into the repo or the

store (.claude/rules/session-data-privacy.md).

CLI Specification

The CLI is the user's surface onto the stages (architecture.md): analyze

populates the store, the views and sql read it, and optimize hands the

findings to an interactive claude session. This spec defines the command

contract and the reporting model; exact flag spellings live with the

implementation and stay in sync via .claude/rules/spec-sync.md.

analyze ― populate the store


saniwalens analyze [--projects <dir>] [--config <dir>] [--db <path>]

Reads both Claude Code inputs ― session transcripts (default

~/.claude/projects/) and live config (default ~/.claude/ plus the relevant

project .claude/) ― and writes the SQLite store (storage.md). That

~/.claude root is $CLAUDE_CONFIG_DIR whenever that variable names a

non-empty path ― an empty value carries no location and is treated as unset ―

so saniwalens follows a config tree the user has relocated instead of reporting on

an empty default. Incremental and idempotent: unchanged transcripts are skipped,

changed ones replaced, the surface catalog rebuilt from current config

(storage.md). The verb is analyze, not build ― it analyzes raw input into

facts.

analyze reads everything read-only and never copies input into the repo or

the store beyond the derived facts (.claude/rules/session-data-privacy.md).

--db ― one store per user, not per directory

Shared by every command. The input is not scoped to the current directory ―

analyze walks *every* project's transcripts under ~/.claude/projects ― so a

cwd-relative default would contradict the data it holds: it would build a

separate copy of the same cross-project store per directory saniwalens is invoked

from, and leave a database file inside unrelated Git working trees. The default

is therefore user-level, ${XDG_STATE_HOME:-~/.local/state}/saniwalens/saniwalens.db

(Session::open in session.rs, which owns resolution, the legacy-store move,

and the guarded open as one seam), with the directory created on demand by

Store::open ― owner-only, like the store itself (storage.md). A non-absolute

XDG_STATE_HOME is invalid per the XDG spec and ignored ― honoring one would

reintroduce exactly the cwd-relative store this default exists to avoid.

State and not cache ($XDG_CACHE_HOME) because the store is not regenerable.

It is built incrementally from the transcripts, but Claude Code prunes those on

its own retention schedule, and the rows already extracted are then the only

surviving record of those sessions ― nothing on disk can rebuild them

(storage.md). A cache directory is by definition somewhere a cleaner may empty

without asking, which is the one thing this file cannot survive; that the store

migrates in place rather than being discarded on a schema change is the same

premise applied to upgrades. A project-local store stays available by asking for

it ― --db ./saniwalens.db.

config.toml ― defaults and named profiles

The tool's own config file lives at

${XDG_CONFIG_HOME:-~/.config}/saniwalens/config.toml (config_file_path in

session.rs; a relative XDG_CONFIG_HOME is invalid and ignored, like its

XDG_STATE_HOME sibling above). The file is optional ― without it every

invocation behaves exactly as before.


default_harness = "kilocode"   # claude | opencode | kilocode


language = "ja"                # en (the default) | ja





[profiles.work]


harness = "claude"


db = "work.db"                 # relative to the config file's directory

It holds two kinds of defaults plus named profiles --profile selects.

Resolution order, strongest first: explicit flags, the selected profile, the

file's top-level defaults, then the builtins (claude, the per-harness store

path). language follows the same strongest-first shape minus the profile

layer: --language, then the file's top-level language, then the locale

fallback, then English. The locale fallback reads LC_ALL over

LC_MESSAGES over LANG (POSIX order, empty counts as unset), then the

LANGUAGE priority list's head (ja_JP:ja votes ja_JP) — Japanese only

when the voting value's leading subtag is ja (ja, ja_JP,

ja_JP.UTF-8); a bare-C / POSIX winner suppresses LANGUAGE entirely

(gettext's C priority — LANG=C.UTF-8 is not bare, so it still defers to

LANGUAGE); C, an empty value, and anything else keep the English

default, byte-identical to before.

Profiles never carry it, so selecting a profile never blocks the file default.

Flag *values* (--scope, --format) are parsed before the session is

built, so an invalid flag fails on its own ― no store open, no freshness line

ahead of the error. The report views resolve those flags through the

windowed dispatch in cli/window.rs: WindowedDispatch::open for the four

views without --scope (format, then period, then Session::open_read),

open_scoped for the three with it (inventory, waste, failures: scope,

then format, then period, then the store), open_scoped_table_json for

doctor (the same scope-first order, with the table | json vocabulary of the

section below), and open_pair for trend (format, then pair, then the store).

The narrowing is carried by what each entry returns ― open gives a

WindowedRead (session, format, window), so the views that never filter have

no filter to ignore, and only the scoped entries (open_scoped /

open_scoped_table_json) return a ScopedRead (that read plus the filter

--scope selected); optimize is the exception that resolves the store path

first, exactly as the pre-Session dispatch did. A relative db joins the directory holding config.toml ― never the

current working directory ― while an explicit --db is taken as is, even

when relative; ~ is not expanded. Unknown keys are ignored so a newer file

never breaks an older binary. A missing file is silence, not an error; anything

else wrong with the file (unparsable TOML, unknown harness, missing profile,

unknown language) fails the invocation with the file named, and an unknown

--profile lists the available ones while an unknown language lists the

valid values (en | ja).

Views ― read the store


saniwalens <view> [--scope global|project[:<slug>]] [--by <bucket>] [--frozen]


              [--format table|markdown|json] [--db <path>]

Each view is its own top-level command; their queries only read the store, never

raw input. The set is deliberately curated ― a view earns a command by carrying

logic a one-line query cannot (a classification, an algorithm, a suggestion). Any

*other* slice is a sql query (below), so thin "just count a column" views are

not commands.

Freshness ― reads auto-refresh

A stale store the user cannot notice was a real failure mode, so a read command

**runs the incremental analyze stage first by default** ― the same composition

optimize always had (architecture.md). With ingested_files skipping

unchanged transcripts (storage.md), an up-to-date store costs one stat per

transcript. The refresh reuses the roots recorded in meta (projects_dir),

and a missing db is simply created ― "absent db" is an error only for sql.

--frozen suppresses the refresh and reads the store as-is.

Every read prints a one-line freshness header on stderr (stdout stays clean

for pipes): what was refreshed, or ― under --frozen / sql ― how old the

store is, with a re-analyze hint once it is older than a day.

Scope ― route each finding to the config layer that owns the fix

"Optimize my global setup" and "optimize this project" are different tasks, and

mixing them lets one busy project drown the global picture. Every finding is

routed (core::scope):

  • Config wedges route by the surface's own scope column (storage.md).
  • Friction categories route by concentration: a strict-majority project owns

the category (fix in that project's config); a spread category is global (a

cross-project habit).

  • Thrash routes to the project it happened in ― carried on the episode

itself, since an episode is scoped to one session and therefore to one project

(events.md); cd% / prompting / token totals are behavioral, hence global.

--scope narrows a report to one layer: global, project (all projects), or

project:<slug> (one). doctor, the optimize briefing, and (by default) the

scoped views show both layers split into sections rather than a merged

ranking.

View Answers
doctor The entry point: a one-screen health check written for someone who has never seen saniwalens's vocabulary ― every item says what happened, why it costs, and what to do. Sections: WHAT TO FIX FIRST (recurring problems as a prioritized to-do list, each routed to the owning config layer with the follow-up command), COST (the session-start context and output totals in plain words, humanized units, naming the agent types behind the subagent figure ― and, when the named rows cover only part of that figure, saying so first; see *Reporting honesty*), CONFIG WORTH PRUNING (dead or heavy config per owner), LOOKS HEALTHY (what explicitly needs no action). --scope narrows to one layer; the text form leads with actions, never a stats dump.
inventory The catalog×usage join per surface row (scope and owning project shown; usage attributed under per-project shadowing ― surfaces.md): startup cost, static cost, load mode, usage. --scope filters to one layer; orphaned usage (no scope to filter on) appears in the unfiltered view only.
usage Skill event rollups: per skill, or per time bucket (--by) ― frequency, tokens, ctx_growth, duration. Leads with a token-destination line (main-thread skill output vs subagent total) so the reader sees where tokens actually go before the table, then splits the subagent half per agent type (runs and output tokens, costliest first) ― the aggregate is usually the larger number and the split is the part that can be acted on. JSON carries the split's coverage as agent_split in every state. In text, a partial split prints its covered and uncovered figures between the total and the table, an unavailable split (no rows at all) is warned on stderr, and rows that cover the total need no note (see *Reporting honesty*). A section with no rows is omitted rather than rendered as bare headers.
models Where the tokens went, by model: main-thread usage events and subagent runs grouped per model, costliest first. tool_error rows are excluded (their model is the originating tool, not a model); missing models bundle as unknown (bundled, never dropped). A note calls out a model holding four fifths or more of the window. The curated logic beyond one sql line: the unknown bundling, the tool exclusion, the deterministic order, and the concentration note.
trend How usage moved: each kind of event (count / output tokens / duration), each skill (invocations, largest movement first), each used surface (kind/id, largest movement first), and the session / subagent totals ― this window against the equal-length window right before it (default 7d vs the 7d before; --last or --since [+ --until] fixes the current one, the pair resolved by the Period section's rules). A kind renders the metrics it carries: point kinds render the count alone, because ingest writes their output tokens and duration as constant zeros (events.md: a span is currently skill_invocation only) ― their rows for those metrics are omitted rather than rendered as 0.0 / n/a, and --format json keeps every kind's three metrics (the machine contract; only the table omits what cannot apply). Every rendered row carries both windows' values, the delta, and the direction; a comparison is n/a / "unavailable" with no delta claimed only when *that row's* previous side holds no baseline, never a drop to zero, and the n/a reason text rides only with a report that holds that comparison (see *Reporting honesty*). Both windows' ranges ― the current one and the equal-length one derived one second before it ― are disclosed like every view's window is, and a pair whose either window leaves the calendar the Period section names is refused as a period error rather than disclosed with an empty bound; --format json carries them as window.current / window.previous. A section with no rows (e.g. no skill usage in either window) is omitted rather than rendered as bare headers.
waste Just the flagged opportunities (unused, costly+rare, always-on heavy, …) with their evidence and owning scope; --scope filters to one layer. Rows with an unknown load_mode label are excluded from routing and reported as a stderr warning plus JSON unknown_load_modes {count, labels} (see surfaces.md).
overhead Reconcile the empirical always-on floor (the leanest observed session start, not the context a skill happened to run at ― surfaces.md) against the readable always-on config; the residual is the system prompt + built-in tools + MCP schemas the catalog cannot weigh. The per-project table carries the session count behind each floor, because the floor is a minimum over observations and a project with few sessions may never have caught a fresh one. Reports the metric as unavailable when no session start was observed at all.
prompts How the user steers the session: the mix of steer / correct / question / instruct prompts (core::prompt, lexical heuristics), with a verdict ― heavy steering suggests more autonomy, frequent correction suggests clearer upfront specs. This is a behavioral signal, not a config metric; embeddings showed prompt *topics* do not map to reusable skills, so the value is in *how* you prompt, not *what about*. Below the mix, repeated prompt shapes (masked templates, three or more sightings) list as candidate new skills with a count, an exemplar, and their sources; rotated or missing transcripts count as pruned.
failures Where the work stumbles: recurring tool failures by category (core::friction ― edit-precondition, path-not-found, blocked-by-hook, …), ranked, each with what it suggests fixing and the originating-tool split. This analyses the *work*, not the config ― where the real cost is. The classifier separates fixable friction from non-actionable noise (cancelled, transient). --scope follows the routing above: global = spread categories, project = each project's majority-owned categories, project:<slug> = everything in that one project (this subsumes the old --project flag). Denials are categorised from the transcript's own denial marker; everything else by lexical heuristics. A stored category the classifier does not know (typo, schema drift) is still listed, but warns on stderr and is counted in JSON unknown_labels {count, labels} instead of silently joining Other.
stuck Bursts of rapid re-edits to one file by one session (core::thrash ― N+ edits within a few minutes), ranked. This isolates *where Claude got stuck and kept retrying* from healthy spread-out editing ― an algorithmic signal a flat edit count cannot give. Observed: a file edited 25× in under 8 minutes. The table carries the project; --format json adds the session id and full path, which is what makes an episode investigable.
sessions Every session in the window: output tokens (events plus the session row's subagent total), wall-clock span covered, and tool-error count ― quiet sessions read 0, never vanish. `--sort tokens duration friction` (default tokens) orders largest first with the session id breaking ties, so the order never churns.

Trend's per-metric reason. A comparison is n/a / "unavailable" only when that

row's previous side holds no baseline ― its kind, its skill, or a session on the

totals axis absent from the previous window ― and never because the baseline

measured zero: a row whose aggregate exists in the previous window compares at

its measured value, zero included (a 0-token span is a measurement, and so is a

session that ran no subagent). Every metric's JSON object carries reason

beside its direction: null when the comparison was judged,

"no_baseline" when the previous side is absent, and "not_applicable"

when the kind does not carry the metric (see *Reporting honesty* and the

machine contract below).

Output formats ― human vs machine

Every command has both a human form and a machine form, strictly separated:

  • Human (default table, plus --format markdown for pasting into

notes/PRs; doctor and analyze have their own text layouts instead of

markdown). The output must explain itself: every table opens with a dimmed

framing block saying what the view shows and how to read it (table

format only ― markdown stays a bare table), headers are words rather than

abbreviations, and interpretation notes are dimmed footnotes. ANSI styling ―

headings, dimmed context, highlighted counts and staleness warnings ― turns

on only when stdout (stderr for the freshness line) is a terminal,

NO_COLOR is unset, and TERM is not dumb; pipes and captures always get

plain bytes. Styling is applied after column padding so it never skews table

alignment.

  • Machine (--format json, on every command): a typed JSON document alone

on stdout ― SQLite integers/reals/NULLs stay JSON numbers/null

(Store::query_json), doctor emits the routed findings structure

(core::optimize::Findings, projects filtered by --scope), and each view

emits its rows as named objects. trend's rows and its JSON are two forms

of one typed payload (trend_payload in cli/views/trend.rs): both derive from

it, so a metric's delta, direction, and reason are judged once ― float

metrics at the display's 0.1 precision, so a drift smaller than the shown

0.1 (an ms-derived duration's addition error) reads as same in both

forms; a golden test (tests/trend_json_golden.rs) pins the emitted JSON.

Every trend metric carries reason beside its direction: null when the

comparison was judged, "no_baseline" when that row's previous side holds

no aggregate, and "not_applicable" when the kind does not carry the

metric. The values are the payload's UnavailableReason enum serialized

(machine-readable only, never prose), and direction == "unavailable"

exactly when reason is not null, so a consumer distinguishes "nothing to

compare against" from "this metric does not apply" without inferring it

from the numbers. All

freshness/refresh chatter goes to

stderr (see above), so saniwalens <cmd> --format json | jq needs no

filtering. Human-only footnotes (row counts, heuristic caveats) are either

folded into the JSON (total, …) or dropped, never mixed into it.

doctor's human form is its own text layout rather than a table pasted as

markdown, so its --format vocabulary is table | json and nothing else:

markdown (and the md shorthand that resolves to markdown in the other

views) is refused at the flag stage ― `unknown --format 'markdown'

(table|json)` ― before the refresh, the freshness line, or the store's

creation, as the flags-before-store contract above requires. The other

windowed views (trend included) take all three values.

Slices not covered here ― the Bash command mix, the most-edited files, an error

category broken down any way ― are a sql one-liner; those once had thin

commands/hotspots views, dropped once sql existed.

Guided entry ― pick instead of typing

Running saniwalens with no subcommand on an interactive terminal, or with

the explicit tui subcommand, opens the guided entry instead of a report:

it asks which agent harness is in use, what to look at, and which scope, then

runs the equivalent report command. The implementation lives in

cli/views/guide.rs; this section states the contract, not the code.

Entry conditions: no subcommand *and* stdin and stdout both TTYs, or the

explicit tui subcommand. A --harness (or --profile) flag given with

either entry is a preset: step 1 is skipped and the named value is used. A

--language flag given with either entry is also a preset and rides the

entry into the inline next step below, but it selects no harness, so step 1

is still asked. Any other token ― a real subcommand, --help, --version ― belongs to clap,

and the guide never intercepts it.

The four steps, each with a default (empty input keeps it,

q quits the guide): (1) pick the harness ― claude, opencode, or

kilocode, defaulting to the resolved value; with a --harness (or

--profile) preset this step is skipped and the resolved value is used;

(2) pick the purpose ― doctor (health check), waste (prune

candidates), or failures (recurring friction); (3) pick the scope ― all

history (no --scope flag), global, or project; (4) after the report,

then the guide offers to run the printed optimize command inline (default

no), then answer the config save question below. At the inline-run question

q counts as no rather than quitting the guide. The chosen harness is kept

for the whole invocation: after each report the guide asks whether to look

at one more (default no) and loops on y back to the purpose, never

re-asking the harness.

Output is always the table form: the guide takes no --format and no period

flags. Before running, it echoes the equivalent command line (e.g.

saniwalens --harness kilocode waste --scope global); after the report it

echoes the executed command again. The reproducible artifact is that command

line, not the session ― the report itself is the same table the command

would print.

After the report, the guide asks whether to save the used harness to

config.toml: skip, set it as default_harness, or store it under a named

[profiles.<name>] profile. The edit is line-preserving ― only the one line

(or section) changes, comments and everything else stay untouched ― and the

guide shows the path plus the changed excerpt and asks for confirmation

before writing. The write re-reads the file first and aborts with a conflict

error when it changed since the dialog read it (last-writer-wins would

silently drop the other edit); the replacement itself is an atomic rename

through a pid-unique sibling temp file, so a mid-write kill leaves either

the old or the new config, never a truncation.

Non-TTY behavior: the explicit tui subcommand without both TTYs is refused

with an error instead of blocking on unreadable prompts; a bare no-args

invocation without both TTYs falls through to clap, whose

missing-subcommand error is what scripts see today. The scripted E2E suite

(tests/guide_flow.rs) drives the real binary through piped stdio by setting

SANIWALENS_TEST_FORCE_TTY=1, which counts as a terminal for the check above;

the variable is test-only and unsupported, and must never be set by users.

v0.5.4 scope is doctor / waste / failures plus the config save above.

optimize itself stays out of the guide, but after each report the guide

prints a next-step line pointing at it with the matching scope

(e.g. saniwalens optimize --scope global); the line is harness-aware, so on

a headless harness it carries --apply (e.g.

saniwalens optimize --scope global --apply), matching the handoff the

inline run actually performs; the remaining reports, period

flags, and sql stay out. The inline run branches on the harness's run mode:

a headless harness has no dialog partner in the seeded session, so the guide

hands off (--apply: the plan is saved and the harness's own interactive

session opens on it); an interactive harness already sits in a dialog, so the

plain inline optimize applies its own plan. The inline run carries the

resolved advisor language into the prompt in the same order

as optimize (--language, then the file's top-level language, then the

locale fallback, then English); with no language set anywhere the prompt

renders byte-identical to before.

The candidates and their order are

declared in

the design doc's post-v0.5.5 expansion note

(docs/exploration/2026-11-06-guided-tui-design.md).

Period ― narrow a report to a window of the history

The windowed report views above take --since / --until / --last so "what did

the agent cost last week" is a view flag, not a sql query. The other commands

(analyze, sql, optimize) take none ― they are whole-history by contract.

Which commands are windowed is derived from the subcommand tree (a command

carrying --last), never a hand-maintained list: every subcommand

must resolve to windowed or whole-history, and tests/cli_help_golden.rs pins

that partition beside the --help captures.

trend resolves the same flags as a pair ― the current window plus the

equal-length window immediately before it (the previous ends one second before

the current starts, so no event is counted in both). --since alone runs the

current window to now ― a bounded window, unlike the single-window views' open

end ― and --until alone is an error: with no current start, the window to

compare against is undefined.

  • --since DATE / --until DATE: a named-day window over the history, each

date a whole day (YYYY-MM-DD, read in the presentation zone ― JST, the

same zone the bucketing table uses; the comparison is against the UTC epoch

the store keeps). --until is inclusive: the whole named day counts.

The resolved instants carry the same calendar bound the rolling span has,

checked at the same resolve entry: the day end adds its +86,399 after the

zone conversion, so a west offset (the --tz zone Time bucketing declares,

not wired into the period path) can resolve NaiveDate::MAX's last second

past the calendar's ceiling, and a date whose resolved midnight or last

second leaves the calendar is refused with the empty-window error naming

its flag. Under JST the named-day path stays inside the calendar on its

own ― NaiveDate::MIN's midnight sits below the floor, where the zone

conversion refuses it as a local time ― which is why the bound is

established at the entry instead of trusted to the zone's sign.

  • --last SPAN: a rolling window ending now ― <N>d, <N>h, <N>w.

Exclusive with the explicit dates (clap conflict), so "last 7 days" can never

be silently reinterpreted by a stray --since. The conflict is declared once

on the shared period-flags group the single-window views flatten

(cli/window.rs); trend's pair keeps its own declaration, so its

pair-specific help wording survives (the help capture pins hold every view's

help byte-identical). The span's resolved window

must stay inside the calendar chrono can express (NaiveDate's range,

roughly ±262,000 years, NaiveDateTime::MIN/MAX's timestamps): a span

whose resolved window leaves it (e.g. --last 100000000d) has no date to

name, so it is refused at the resolve entry with the same invalid-span error

as an unparseable one. trend's pair resolves through the same entry, so a

current window outside the calendar is refused there too ― and so is the

derived previous window, the equal-length window the pair builds one

second before the current one: --last reaches back twice, so a span whose

current window still resolves can start the derived previous below the

calendar (e.g. --last 50000000d), refused with the same invalid-span

error. The date-derived pair has the same bound: a --since whose

equal-length derived previous leaves the calendar (e.g.

--since=-200000-01-01) is refused with the empty-window error naming

--since ― the input is the date, so the invalid---last wording would

blame the wrong flag.

  • Errors are parse-time, before any report renders: an unparseable date fails

on stderr with a non-zero exit and an empty stdout; --since after --until

is an empty-window error rather than an empty-looking report. A --last

whose resolved window leaves the calendar is that same invalid-span error,

and a named day whose resolved midnight or last second leaves it is the

empty-window error naming its flag ― non-zero, empty stdout, before any

report renders or store work runs.

  • The window is disclosed, never silent: a dimmed report window: line

rides with the freshness line on stderr (every format), the framing block

carries it as its last line (table only ― markdown stays a bare table),

doctor prints it in-band under its heading, and --format json gains a

window object (since / until as RFC 3339 with their offset). Every

accepted window renders a bound that names its instant, never an empty

string: an in-calendar instant renders in any valid zone, so the bounds

renderer has no empty-string fallback to absorb an out-of-calendar bound

with. Two limits belong to the presentation, not to the window. At the

calendar's own ends the rendered wall clock sits at most one zone width (less

than a day) outside the calendar while the instant it names stays exact and

in-calendar, and the spelled-out local date is at most one day outside ―

the ceiling rendered in JST is +262143-01-01T08:59:59+09:00, a date

NaiveDate cannot name. Only a clock within a day of ±262,000 years reaches

either, so a real run cannot. And RFC 3339 names years 0000..=9999 only, so a

render at the calendar's edge years has the RFC 3339 shape but does not parse

back as RFC 3339. The tests pin both ends byte for byte

(the_presentation_spill_at_a_calendar_end_is_pinned_byte_for_byte in

src/core/period.rs).

Without the flags every output is byte-identical to the pre-period behavior.

  • The catalog half of inventory is current config, so it is not windowed by

time ― its usage half is. An unused row under a window says

UNUSED (window) / "unused-in-window", never plain "unused".

  • Sessions the writer could not stamp (no observable start, empty

started_at) are excluded from a windowed session_stats /

subagent_totals figure (store.rs's <> '' guard) rather than guessed

into it; without the flags they still count.

  • The windowed readers that scan events read the store through

started_epoch, and the store grows with every analyze. The store declares

the index that keeps those reads fast (storage.md) and creates it on the

next read-write open; --frozen / sql (read-only) never create it, so a

store not opened read-write since it was declared keeps scanning. The

sessions-axis figures read sessions.started_at instead ― a small table no

index needs to serve. Watch the size with

saniwalens sql "SELECT COUNT(*) FROM events".

Time bucketing

--by groups by year | month | week | day | hour. Because the store keeps UTC

(storage.md), bucketing converts to --tz first (default JST) so day/hour

buckets mean the user's local day/hour ― bucketing UTC would smear a local day

across two buckets.

--tz takes an offset, not a zone name, and its domain is minute-granular:

-86,340..=86,340 seconds in 60-second steps (±23:59), 2,879 offsets.

FixedOffset::east_opt also accepts a seconds remainder, but a bound renders

the offset with %:z, which rounds to the nearest minute ― a remainder would

be silently rounded in the report, and the ends of the unbounded seconds

domain (±86,399) would render +24:00, which is not a valid offset. The period

path does not read --tz yet (Period above); the domain is declared here so

wiring it cannot widen the rendering silently.

A span is assigned whole to its start-time bucket; its cost is not split

across boundaries. This is correct for coarse buckets (year/month) and for

counting, but distorts fine buckets for long spans: a loop span lasting

hours (observed ~10,000s) lands entirely in one hour even though its work spanned

many. So at --by hour / --by day, the report flags long and trailing spans

(events.is_trailing, and a duration threshold) rather than letting them build a

silent spike. Duration-weighted distribution is a later option; v1 assigns to the

start bucket and is honest about the limitation.

Reporting honesty

The report never hides an approximation; it labels it (these mirror the metric

caveats in events.md / surfaces.md):

  • sub_tokens_estimated rows are marked so estimated subagent cost is not read

as exact.

  • Trailing spans (closed only by session end) are marked; their duration is a

lower bound.

  • Surfaces with unknown static_tokens (e.g. mcp_tool without an available

schema) are marked unknown, never reported as zero cost.

  • A surface's startup cost and its on-demand body cost are shown as two figures,

never one (surfaces.md): a skill's body is what invoking it costs, so

printing it alone under a "what to trim" heading reads as a startup saving the

deletion never delivers.

  • "Unused" always carries the window it was evaluated over, so it is not mistaken

for "never installed": without the period flags the window is all history, and

under --since / --until / --last the row itself says UNUSED (window)

(inventory; the other views' empty states read "in the evaluation window").

  • A window the input makes unresolvable is an error, never a silent

report: a --last whose resolved window ― or, in trend, the equal-length

window derived one second before the current one ― leaves the calendar

names dates that do not exist, and fails with the invalid-span error; a

--since whose derived previous leaves it fails with the empty-window

error naming --since; and a named day whose resolved midnight or last

second leaves it fails with the empty-window error naming its own flag.

The alternative would be a disclosure line with an empty since and a

store bound (started_at >= '') that silently passes every session ― a

successful-looking report that measures nothing. The bounds renderer keeps

no empty-string fallback to absorb an unrenderable instant with: an

accepted window's instants are in-calendar by the resolve entry's check, so

a bound always renders, the disclosure line and the JSON window cannot

carry an empty string, and the one-zone-width presentation spill at the

calendar's own ends (qualified in the Period section) is pinned by a test

instead of being passed over as if it named a valid date.

  • A subagent run whose agent type was never recorded is shown as (unknown),

never merged into a named type and never dropped ― the per-agent rows must

keep summing to the subagent total the same report prints above them, for

every run that could be extracted (the two cases below cover the runs that

could not).

  • When they *cannot* sum to it ― a store predating the per-agent split, read

with --frozen so the refresh that would fill it never ran ― the report says

so on stderr instead of letting an absent breakdown pass for a zero one

(storage.md's report-the-gap contract). It rides with the freshness line

rather than in the table, so piped stdout and --format json stay clean.

Under a drawn window an empty split is usually the two time axes at work ―

the total reads the session's stamped start, the rows read each run's own

epoch ― so the message names the window instead of pointing at a refresh

that cannot fill a straddle; the refresh hint stays without the flags.

  • When they sum to only *part* of it ― sessions analyzed before runs were

extracted keep their totals (storage.md: the store outlives its inputs), but

once Claude Code has pruned their transcripts no refresh can ever produce their

rows ― the rows are labeled a partial split in-band, beside the numbers

they qualify, because this is a property of the data and not a staleness a

refresh could cure: usage prints the covered and uncovered figures between

the total and the table, doctor states the gap before naming any agent, the

briefing does the same under its subagent line, and JSON carries the

reconciliation as agent_split (core::subagent::SplitCoverage). Under a

drawn window the same gap is the straddle, so the in-band labels say the

uncovered tokens fall outside the report window instead of the

pruned-transcript reason; without the flags the wording is unchanged.

doctor introduces its top rows as "most of" the subagent output only when

they exceed half of the total ― a long tail, or a partial split, gets a

wording that claims no more than the rows show.

  • An n/a in trend states its real reason, and the reason is a fact about

that row: its previous side holds no baseline ― no event of that kind, no

invocation of that skill, or no session on the totals axis. It never means

the baseline measured zero, and never a drop to zero. The table's reason

text names that row scope ("that row's previous side") because one sentence

covers the kind, skill, and totals sections, and it is printed only when a

report actually holds such a comparison; the footnote about an empty

previous window is printed when that window holds no event of any kind. A

session alone does not suppress it: the note speaks about events, and the

totals rows may still compare while the kind rows are n/a. A metric a kind does not carry renders no row at all ― the table

omits it, so the unavailable label is never attached to a metric the table

does not show. --format json keeps every kind's three metrics for its

consumers, holding the same shape with a null delta and

"reason": "not_applicable" where the kind carries nothing,

"reason": "no_baseline" where the previous side is absent, and

reason: null where the comparison was judged. A baseline that measured

zero still compares: a 0-token span is a measurement, a session that ran no

subagent measured 0 runs, and a baseline that only rounds to the displayed

zero compares too. Count axes keep their baseline tied to the aggregate

row's presence, deliberately: a window with no event of a kind stays

no_baseline rather than reading a 0 -> N change as a measured move. A

byte-identity criterion stated for this view by an earlier refactor is

withdrawn, and two deliberate output changes replace it: a report holding a

measured-zero baseline now compares its cells instead of printing n/a, and

a report that holds any n/a comparison prints a one-line reason sentence

whose wording names the row scope (that row's previous side) so it covers

the kind, skill, and totals sections. Pinning output that the spec forbids

is what the criterion did; the invariants above, each pinned by a test, are

what stands in its place.

Meta-skills are not nested (events.md): a driver and the skills it ran are

each their own span, so a child's cost lands on the child and no figure is

silently double-counted.

When several caveats apply to one row ― e.g. a long loop span that is

trailing, holds equally-split subagent tokens, and is bucketed whole into one

hour ― the row is marked low-confidence overall, not merely tagged three

times. Stacked approximations compound into exactly the kind of time-concentrated

spike a reader over-trusts; one combined flag says "read this number loosely".

sql ― query the store directly


saniwalens sql [<query>] [--format table|markdown|json] [--limit <N>] [--db <path>]

sql is the one read that never auto-refreshes ― it opens the store strictly

read-only, so an ad-hoc query is reproducible and can never mutate anything.

It prints the freshness header (store age) on stderr instead, so a stale read

is at least visible.

The store's own query surface: run an arbitrary read query and print the result.

The query is the argument, or ― when omitted ― read from stdin, so both

saniwalens sql "SELECT …" and echo "SELECT …" | saniwalens sql work (stdin

sidesteps shell quoting for complex queries). This exists because the tool is a

*session-analysis* tool: anyone wanting a slice the fixed views do not cover ―

notably the optimize session chasing a root cause ― should query the analyzed

store, not re-parse the raw transcripts. The store is opened read-only so an

ad-hoc query can never mutate the derived data, and an absent db is an error

(run analyze first), not a silently-created empty one.

A tool_errors view (storage.md) names the friction columns that are

otherwise overloaded onto generic event columns (category, excerpt, tool,

target, project), so a friction query reads cleanly without knowing the

encoding ― e.g. `SELECT target, COUNT(*) FROM tool_errors WHERE

category='edit-precondition' GROUP BY target` answers "which files keep failing

to edit", which the error text alone cannot. SELECT sql FROM sqlite_master

lists the full schema.

Result rows are bounded: at most --limit rows materialize (default 10000,

0 disables the bound). A truncated result warns on stderr with the opt-out,

so the "any slice" contract stays reachable without ever passing a partial

slice off as complete; the JSON payload keeps its bare-array shape. The SQL

text itself (argument or stdin) is unbounded — it is user-supplied input, not

an amplification: only fetched rows balloon memory, and those are capped.

optimize ― act on the findings with an advisor session


saniwalens optimize [--projects <dir>] [--db <path>] [--scope global|project[:<slug>]]


                [--frozen] [--print] [--verbose] [--timeout <DURATION>] [--apply]


                [--language en|ja]

The AI-proposal consumer (architecture.md): rather than emit static

"recommendations" the tool cannot safely act on, optimize analyzes (unless

--frozen, the same flag the views use), composes the findings with a prescribed advisor prompt, and

launches the harness's agent seeded with it ― claude for an interactive

session that applies edits on agreement, opencode run --format json for a

headless run that streams only the agent's text while the raw tool output

logs to a private file (--verbose restores the raw stream) and prints the

plan without editing. The headless output opens with a proposal-only status line stating no files were changed, so a truncated read still shows it. The private log lives for the whole run; a failure

keeps it and is named in the error, so a failed advisor still leaves its full

output reachable, while a success removes it (the raw stream may echo

secrets) unless SANIWALENS_KEEP_RUN_LOG=1 keeps it for post-mortem

inspection; the run's child and heartbeat thread are torn down on every exit

path, not only on

success (cli/headless.rs). --timeout <DURATION> (e.g. 30s, 2m, 500ms)

bounds a headless run; when it expires the child is killed and reaped and the

error names the raw log. It is off by default, so a legitimately long run is not

cut short. The prompt makes

the session investigate autonomously to a conclusion: it pins down each root

cause and proposes a concrete fix, rather than handing the analysis back with a

"which area do you want to start with?". It prioritises work friction over config

size, verifies before recommending removal (an "unused" skill may be invoked by

subagents) by inspecting rather than asking, and ― in interactive runs ― pauses for exactly one thing ―

approval of the concrete fix-plan before any file is edited. This "drive to a

plan, gate only on applying it" shape is the design; if it changes, update

instructions in core::optimize and this paragraph together.

instructions renders from the harness copy (HarnessCopy), not a constant,

so the advisor identity, config locations, and raw-input pointers name the

harness whose rows the briefing renders.

--language en|ja (and the language config key, the same flag-beats-file

order with the locale fallback beneath them)

switches the advisor's output language. The instruction is one sentence from a

single source (AdvisorLanguage::instruction_sentence in core::optimize,

carried on the same HarnessCopy): the briefing instructions, the headless

instructions, the apply instructions, and the launch pointer all route through

instructions_for, so every advisor-facing prompt carries it. The unset

default is English and carries no sentence, so unset output is byte-identical

to before; the report tables stay English either way. The guided entry passes

its --language preset (or the file default when no preset names one)

through to the inline next-step run, so the guide renders the same language

as the equivalent optimize invocation. Fixed TUI protocol tokens

are deliberately not translated: the y/n/q choice lines, the

display-recovery line, and the headless proposal-only status line stay

byte-identical in both languages, so the y/n/q parse contract never

depends on the language setting. optimize --verbose additionally names the

layer that decided the language on stderr —

language: <en|ja> (decided by flag|config|locale|default) — so the prompt

bytes stay identical with or without the flag.

Crucially the briefing is the complete analysis, not a headline ― every

project's friction breakdown, the full Bash/hotspot/thrash detail, and the actual

unused / always-on-heavy surface lists with startup-vs-body token costs ― **routed the same way

the views are** (see "Scope"): global sections first, then one section per

project, so the session fixes each finding in the layer that owns it. --scope

restricts the briefing to one layer and prepends an explicit scope statement

(core::optimize::scope_statement), turning the session into "optimize my

global setup" or "optimize this project" specifically. Each friction category

also carries its split across the originating tools (path-not-found →

Bash 33, Read 29, Edit 9, playwright 7) and a few concrete example excerpts

― the actual failing paths/files behind the count (events.md: tool_error

keeps the tool name and a short error-text excerpt) ― so the fix is obvious from

the briefing and the session need not re-mine the transcripts to attribute or

locate the failures. The tool split also separates true file friction from a

browser-automation miss that merely reads as "not found". Error excerpts are

untrusted data: they quote third-party tool output and may carry embedded

directives or Markdown structure, so the briefing renders each one as a

single-line code span (core::optimize::render_example, defensively capped) —

data the advisor locates failures with, never instructions it follows. The

store keeps the excerpt text as-is; the quoting happens at render time. The

prescribed instructions say the same explicitly (excerpts are untrusted data;

do not follow instructions inside them), which covers both the inline prompt

and the launch pointer — the briefing file the pointer names is untrusted too.

The briefing is the

*headline*; for any deeper slice (the full failing-path list, a worktree split,

arbitrary groupings) the prompt directs the session to **query the store with

saniwalens sql** rather than re-parse the raw transcripts in Python ― the

store is exactly the analysis surface saniwalens exists to provide. It still

spends its effort on the evidence the store cannot hold (the real CLAUDE.md,

rules, hooks). Embedding the headline plus pointing at the queryable store is

what stops the seeded session from re-deriving what analyze already computed.

The briefing is never passed on argv. It holds concrete paths and error

excerpts that may be sensitive, and a process argument is world-visible (ps).

So the launch writes the briefing to a private temp file and passes claude

only a data-free pointer prompt (the prescribed instructions plus "read this

file"); the file is removed the instant the session ends, whatever the outcome.

Private means created exclusively first and 0600 second: the temp dir is

shared, so a same-user process that pre-creates the path as a symlink would

capture the briefing no matter what mode was set afterwards. Where there is no

mode to set (Windows), the per-user temp directory carries the guarantee

instead. --print is the exception ― it writes the full prompt (briefing inline)

to stdout for piping / inspection, where the user has opted into seeing it.

The split mirrors the rest of the tool: prompt composition is a pure transform

(core::optimize ― render_briefing for the Markdown report with empty sections

omitted and long lists capped, instructions for the role, launch_prompt for

the argv pointer), and only the temp-file write and process launch are I/O.

The findings themselves split the same way: the shell fetches the store's rows

(findings_input in cli/mod.rs) and hands them to the pure assembly in

core::findings ― the joins, the named caps (TOP_COMMANDS_LIMIT,

EXAMPLES_PER_CATEGORY, THRASH_LINES_PER_PROJECT, …), the scope routing, and

the ordering ― so the briefing's wiring is unit-tested over small inputs and

only the queries and the print are I/O. The briefing's store reads are bounded

at fetch time, not only at render time: findings_input uses the *_briefing

readers (a trailing LIMIT over the same WHERE/ORDER BY, so a bounded result

is the head prefix of the unbounded one) with the fetch caps owned by

core::findings (BRIEFING_GROUPS_LIMIT, BRIEFING_EVENTS_LIMIT), skill

invocation output is summed in SQL (skill_out_tokens_sum), and the rendered

briefing is cut at BRIEFING_MAX_BYTES with a truncation marker naming the

store query to run instead ― so a multi-year store yields a bounded briefing,

never silent partial data.

The send is one seam: deliver runs a DeliveryPlan whose mode

(DeliveryMode::Print | Interactive | Headless, chosen by --print over the

harness's launch shape) picks the payload ― Print writes the prompt to

stdout, launch modes write the briefing to the private pointer file, hand the

spawn to the AdvisorLaunch adapter, and remove the file the moment the run

ends. Production wires ProcessAdvisor (inherited stdio, or run_headless's

logged pipe unless --verbose); the delivery tests wire a recording double

and assert the argv instead of spawning. Harness::copy assembles the harness

data those prompts render from, so the shell never spells HarnessCopy field

by field. The launch shape the mode defers to is per-harness **data on the

seam** too (Harness::launch_command in adapter::harness, beside the

harness's other arms), so a new harness's delivery lands there and this

section's wiring stays put. The headless run's raw lines render through

per-harness data as well: the plan carries the renderer the harness seam

chose (Harness::run_line_renderer), and the logged pipe applies it line by

line, so the loop never names a harness and a new harness's stream needs no

shell edit. deliver returns Result<()>, not a typed outcome: its only caller

(optimize) needs success/failure, and a non-zero exit is already turned into

an error naming the raw log; a DeliveryOutcome is deferred until a consumer

needs the status or the log. PBI 57 records this decision.

--apply hands a headless run's plan to the harness's own interactive

session in one command (headless harnesses only): the advisor runs headless

as usual, but its raw log is kept, the agent-text lines (Text only, never

the JSON event lines) are extracted into the plan, and the plan is saved as

$XDG_STATE_HOME/saniwalens/plans/plan-<time>-<pid>-<seq>.md with private

(0600, exclusive creation, like the briefing temp files) permissions. The

path is printed, with a note that pruning saved plans is a separate

command's job: a handoff run always leaves its plan file behind and always

shows its path, while a normal optimize leaves nothing. The harness's own

TUI then opens on an apply-ordering prompt (core::optimize::apply_prompt)

naming the plan file and the store, so the dialog digs out each step's

evidence with saniwalens sql instead of re-parsing raw input:

opencode --prompt for opencode (the expected shape: flag acceptance

verified, with its TUI prompt injection still awaiting one confirmation on a

real TTY), kilo --prompt and

bare claude as before (Harness::interactive_launch_command in

adapter::harness). --apply refuses --print (printing ends the run

instead of handing it off), --verbose (the handoff reads the logged stream

that verbose mode does not keep), and interactive harnesses (their session

already applies its own plan); the flag checks run before any store work.

When the dialog launch fails, the error names the kept plan file; when the

headless run yields no readable text, nothing is saved and the error says

so, and the raw log is removed either way once its text is read (it may echo

secrets). The dialog prompt carries the apply safety contract - per-item backup,

planned diff, explanation, choice, apply-on-y, result summary (core::optimize::apply_prompt).

The session walks the plan one item at a time and never moves to the next item

without an explicit choice on the current one: the former single approval gate

is now per-item approval, with no whole-plan batch approval. Before

touching an item the session copies every target file's pre-edit bytes into

$XDG_STATE_HOME/saniwalens/backups/<timestamp>/ (dir 0700, files 0600;

backups are kept like plans and their path is always reported), covering

git-tracked and untracked files alike, and additionally records

git status --short for tracked ones. It then shows the item's planned diff

(diff -u old-to-new; the file stays unchanged until the choice), explains

the item briefly (why, what it fixes, its risk), and asks the item's choice on

three short fixed lines of at most 24 characters each (y: Apply this item /

n: Skip to next / q: Quit applying) with no file names, line numbers, or

gist in them: the file, line numbers, and gist stay in the diff and

explanation above, never in the choice lines. y applies it, n skips to the

next item, q aborts the whole session. If the choice display looks wrapped

or broken, one line tells the user to resize the terminal and ask for the same

item again.

Only y edits the file. On refusal nothing changes - files stay

byte-identical, backups are kept, and the session says so with the backup path.

A blanket instruction such as "do the rest" never counts as a choice: unchosen

items stay unapplied, and the session restates that each item needs its own

y/n/q. On q the session lists every unprocessed item and declares the

rest unapplied.

The session closes with a result summary in up to two sections (## Applied changes, omitted when nothing was applied, and ## Proposal only (not applied)), where items skipped via n, aborted via q, never reached, or refusing the actual config are listed with why, so

applied stays distinguishable from proposal-only without re-reading the plan.

Saved plans and their backups accumulate without bound, so `saniwalens

cleanup` lists and prunes them (the implementation lives in

cli/cleanup.rs, beside the handoff seam in cli/handoff.rs). A bare run

(or --list) prints every plan file and backup generation with its size

(a generation dir lists its recursive total over the files under it;

links never resolve, so a link counts as a link) and modification time;

entries that cannot be read are skipped without failing the listing and

their count goes to stderr as a warning, so stdout and JSON stay

byte-identical;

cleanup --keep N (a bare --keep keeps 10) deletes all but the newest N

generations in each area, snapshotting every area and printing the count

and total size before deleting anything, then reporting every removed path

through the shared table renderer, so the sweep shows its evidence before

it deletes and the deletion stays inside the generation rule. Only

$XDG_STATE_HOME/saniwalens/plans/ and .../backups/ are ever touched:

every victim is resolved (symlinks followed) and checked against those

roots right before the delete, so an entry pointing outside is reported

skipped and never followed out; a dangling link counts by its own parent

dir and its link is removed; and a victim that vanished between the

listing and the delete is ignored, not an error and not reported skipped.

The command needs no store and opens none, so it works on a fresh machine;

its --format is the shared table | markdown | json vocabulary, with

the machine contract (removed_total, per-area removed / kept /

skipped) on --format json. The default keep of 10 generations per area

is a starting proposal (a handoff run is manual and infrequent, so 10

covers weeks of iterations while bounding the secret-bearing files);

tightening it is a review call.

Surfaces Specification

A surface is one configurable thing in a Claude Code setup — a skill, a

rule, an MCP server, a hook, a permission, an CLAUDE.md, an agent. This spec

defines the surface catalog and the catalog × usage join that is the whole

point of the tool (architecture.md): relating *what is installed and what it

costs* (surfaces, from config-format.md) to *what was actually used and at what

runtime cost* (events, from events.md) to expose optimization wedges.

The catalog

The adapter reads config into one surface per configurable thing, each with:

  • a stable (kind, id) identity — the join key events also carry;
  • two costs, because one figure cannot answer both questions: a **static

cost** (the whole definition — for a skill or agent, what invoking it costs)

and a startup cost (the slice loaded into every session, which is all that

removing the surface reclaims), plus its load mode (startup-full /

startup-description / path-conditional / on-demand / tool-schema — see

config-format.md). Load mode is what separates always-on tax from per-use

cost, and which slice of the text each cost covers;

  • its scope (global vs project) and config_path.

The catalog is the denominator of every optimization question: you cannot call a

surface "unused" without knowing it was installed in the first place. A surface

exercised in a transcript but absent from the catalog (e.g. a skill that was

since deleted) is also meaningful — it is reported as orphaned usage, the

mirror of unused config.

A surface exists at the global scope, in any number of projects, or both. The

catalog keeps every row (scope + owning project), and the join resolves each

event against the effective surface for its session's project — that

project's copy shadows global there, while other projects' events still land on

the global row — so one event never double-counts across scopes and one

project's usage never inflates another's copy (storage.md "Surface identity,

scope, and the effective join"). Scope is also the routing key for reports: a

wedge on a project-scoped surface is that project's finding, not a global one

(cli.md --scope).

**A directory that exists but cannot be read warns instead of reading as

absent.** The OS protects some locations per app (macOS gates ~/Documents,

~/Desktop, ~/Downloads behind a permission prompt), so a catalog scan of a

project there can fail with a permission error. A silent empty result would

read as "nothing configured here" and turn every live surface into orphaned

usage — a wedge the environment manufactures, not found in the input. So a

missing directory stays silent (the scope may simply not exist), while any

other read failure prints one stderr warning naming the directory; the affected

surfaces stay uncatalogued until the permission is granted or the config moves.

Usage-measurable vs catalog-only surfaces

Not every surface kind emits a usage signal, and conflating the two is the

fastest way to a wrong recommendation. Each kind is classified:

Surface kind Class Usage signal
skill usage-measurable skill_invocation
agent usage-measurable agent_spawn
mcp_server / mcp_tool usage-measurable tool_use
permission usage-measurable (partly heuristic) permission_prompt from the denial marker, falling back to denial text — lower confidence
rule catalog-only none (injected context; no invocation event)
hook usage-measurable hook_use (a fired hook_success attachment; its hookName joins the catalog id)
claude_md catalog-only none (always-on; usage is not the question — static cost is)

For a catalog-only surface, absence of events is *not* evidence of disuse —

no event could ever appear. The join still lists it (with zero usage), but the

wedges below gate on this class so a rule is never flagged "unused →

delete" merely for emitting nothing. Hooks left that class once firings became

observable: a hook with firings is used, one without is an unused delete

candidate like any other measurable surface.

Optimization wedges

A wedge is a surface-shaped opportunity. The core computes these from the joined

rows; the report ranks them. None is a verdict — the tool surfaces the wedge with

its evidence; acting (or the future AI layer proposing) is downstream.

Wedge Condition Requires Suggested move

Ranking by what removal actually saves

A wedge is only useful if it says how much *removing the surface saves at

session start* — and that is not its static token count. Skills and agents load

only their description at startup (their body is on-demand), so deleting an

unused one is decluttering, not a token win, even if its body tokenizes

large. Every view that names a surface therefore ranks by startup_savings and

reports the two costs apart — startup_tokens (what removal reclaims) beside

the on-demand body (what invoking it costs), never one figure standing for both.

The ranking (see core::surface):

  • measured tokens — always-on config (startup_full): removing it saves that

many tokens every session. Ranked first, largest first.

  • unknown schema — an MCP server (tool_schema): a real every-session cost

the catalog cannot weigh; flagged, ranked next.

  • declutter — on-demand / path-conditional bodies (skills, agents,

conditional rules): ~no startup cost, so an unused one is namespace hygiene,

not savings. Ranked last and labelled as such.

This stops a view from headlining an unused skill's body size as if deleting it

freed that context, and lifts the genuinely paid items (heavy always-on rules,

unused MCP servers) to the top. The rule binds the optimize briefing as much as

the tables: a briefing line reads `skill/x (~7 tok at startup / 1015 tok when

invoked)`, because the seeded session acts on those figures and a single

unlabelled number there becomes a fix proposal that frees nothing.

The "Requires" column makes the coverage explicit: Unused and **Costly +

rare** apply only to usage-measurable kinds ― never to rule / claude_md. A few wedges depend on signals the tool does not yet fully have:

  • Never-fires rule needs evidence a rule's paths: glob *could* have fired.

The only honest source is session activity — did any file matching the glob

appear as a read target in the window? Read targets are extracted per

tool_use (file_read events, docs/specs/events.md) and the catalog

carries each rule's globs (attrs_json, docs/specs/storage.md); the waste

view flags a rule whose globs matched nothing read, with the globs as

evidence. A window with no read targets at all flags nothing — no evidence,

never an accusation (this also keeps harnesses without read extraction from

false-flagging every rule).

  • Redundant needs a purpose/similarity signal derived from each

surface's description. Skill/agent/command descriptions are catalogued

in the surfaces.description column; the waste view pairs same-kind

surfaces whose tokenized descriptions overlap at least half

(MIN_REDUNDANT_OVERLAP), and lists each paired surface once, naming its

first counterpart. No counterpart, no row ― and a window with no reads at

all is not consulted, since this wedge is config-side, not activity-side.

Identical descriptions always match; CJK text without spaces only matches

identically, which is the documented recall limit.

Load mode is a first-class part of a surface because the same static-token

figure means something very different for a CLAUDE.md paid every session than

for a skill body paid only when invoked — but load mode is an assumption, so the

always-on wedge is confirmed empirically, not asserted:

Always-on reconciliation

static_tokens is a config-side estimate, never a measured runtime component

(config-format.md). To claim "your always-on config costs ~X every session"

honestly, reconcile it against observed context: the **floor of the session-start

context across sessions** is an empirical lower bound on the always-on context

every session starts with. Comparing sum(startup_tokens) against that observed

floor is the only evidence-backed form of the always-on claim. The sum spans

every surface, not just the always-on files: a skill's description is paid at

every session start too, so leaving descriptions out understated the config's

share of the floor by however many skills had accumulated. Surfaces whose startup

weight is unknown (an MCP schema) stay out of the sum rather than entering it as

zero — they land in the unattributed residual, where the report already says the

figure is an upper bound on system + tools + MCP.

The floor must come from an actual session start (the session_start event —

events.md), never from a skill span's ctx_start. Spans were the original

source and are a rejected alternative, not a supported one: a span's ctx_start

is the prompt size wherever that skill happened to run, which in a long or

resumed session is far above what the session started with, so a project whose

only skill invocations came late reported a mid-session size as its startup cost

— inverting the advice this section exists to give.

What still bounds the figure is the observation set, not the source: a start is a

lower bound only for a *fresh* session, since a resumed one begins with its

context already restored. The minimum across a project's sessions filters those

out when there are enough of them, so reports carry the session count alongside

the floor, and a project with no observed session start contributes no floor

rather than a substitute.

This is implemented as the overhead command (cli.md): it reports the observed

floor, the readable config that accounts for part of it, and the residual —

the floor minus the config — which is everything not in the user's files: the

system prompt, built-in tools, and MCP tool schemas the catalog cannot weigh

(config-format.md marks mcp_tool static cost unknown). The residual is how

the tool gives an empirical handle on MCP cost despite not reading the schema:

observed against a real tree, the readable config was a small fraction (~6%) of a

much larger always-on floor, redirecting "what to slim" from rules toward the

tool/MCP surface. Per-project floors are also shown, but they are confounded by

how early in a session a skill was first invoked (a project whose skills only ran

deep in long sessions shows an inflated floor), so the global floor is the

trustworthy baseline; the per-project view is suggestive, not a clean per-server

measurement.

Time and trend

Because events carry a timestamp, every wedge can be evaluated over a window

(cli.md bucketing). "Unused" means unused *in the window*; a surface used

heavily last quarter but never this month is a different signal from one never

used at all. The catalog is current (read now); usage is historical — the report

states the window so "unused" is never mistaken for "never installed".

What the core computes vs. what it leaves open

The core computes the join and the wedge classifications above from thresholds

injected as tuning constants (what counts as "high cost", "low usage"). It does

not rank surfaces against each other by importance, infer intent, or decide

that a wedge should be acted on — those judgements belong to the human reading

the report, or to the optimize AI-proposal session that consumes this same

joined data.

Rows whose load_mode label is unknown to the core (not one of the five known

labels) are excluded from wedge routing — no default mode is assumed, since

any default would misstate savings — and are counted in

ScopedWedges::unknown_load_modes (raw labels; the count is its length). The

core stays pure: the CLI renders the warning and the JSON field from that

count.

Events Specification

An event is one timestamped occurrence the tool extracts from a transcript,

carrying a runtime cost and pointing at the configuration surface it exercises.

Events are the usage half of the catalog×usage model (architecture.md). This

spec defines the event kinds, how a *span* (an event with a duration window) is

bounded, how each cost metric is computed, and how two hard cases — context

compaction and meta-skills that drive other skills — are handled. All of it is

pure logic over the domain model the adapter produces; it is the tool's

primary test surface (.claude/rules/tdd.md).

Event kinds

Every event has a kind and, where applicable, a surface_kind / surface_id

identifying the configuration surface it exercises (the join key into

surfaces.md).

kind Surface exercised Span?
skill_invocation skill yes — work window until the skill's activity ends
agent_spawn agent no — point event; its cost is carried by the run it started (below)
tool_use mcp_tool / mcp_server / built-in tool point event
prompt — (user input; raw material for skill extraction) point event; text referenced, not stored
tool_error — (a failed tool_result) point event; friction category in surface_id, a short error-text excerpt in source, the originating tool name in model, the call's target (file_path / command) in target
file_edit — (an Edit/Write target) point event; the file's basename in surface_id, its full path in target
file_read — (a Read target) point event; same encoding as file_edit. Observed, never attributed: it feeds the never-fires wedge (docs/specs/surfaces.md), not thrash (which reads file_edit only) or hotspots
hook_use hook (a fired hook) point event; the hook's hookName (Event:Matcher) in surface_id, joining the catalogued hook. Firings come from attachment records with type: "hook_success"; context/summary attachments are not executions
bash_cmd — (a Bash invocation) point event; the command's leading word in surface_id
compaction — (a compact_boundary) point marker, used by the context metric
permission_prompt permission point event (friction signal) — partly heuristic source

New kinds are added additively as the adapter learns to recognise new signals

(session-format.md); the schema's loose kind / surface_* columns

(storage.md) absorb them without migration.

Two kinds carry caveats that downstream reports must honour:

  • **prompt** stores a pointer (source_path, source_line) to the raw record,

not the prompt text — the text is recovered on demand by the future

skill-extraction layer, keeping personal data out of the store (storage.md,

.claude/rules/session-data-privacy.md). This reserves the

prompt-clustering capability now so it survives transcript rotation.

  • **permission_prompt** is counted from the denial marker a denying entry

carries, falling back to denial text where there is none (session-format.md).

The marked half is as structural as any other kind; the fallback half is not,

so the friction wedge built on it (surfaces.md) stays labelled

lower-confidence — a transcript written before the marker existed is still

counted by an English phrase alone.

  • **tool_error keeps a short, bounded excerpt** of the error text — unlike

prompt, which stores only a pointer. The asymmetry is deliberate: prompt text

is large and wholesale-sensitive and is needed in full only by a later layer,

so a pointer defers the cost; an error excerpt is small and its *value is the

concrete instance* (the actual failing path), which a report shows directly.

It lives only in the local store (gitignored, never committed), so the privacy

rule — no real data in the repo — still holds.

  • A tool_error's friction category (core::friction) follows two precedence

rules. First, **a concrete cause beats cancelled**: the interruption

patterns are checked only after every specific cause (path-not-found,

edit-precondition, …), so a real failure with an interruption-like fragment

appended keeps its cause instead of vanishing into the non-actionable

cancelled bucket. Second, **short interruption fragments require the whole

message**: tool execution aborted and task cancelled classify as

cancelled only when they are the entire (trimmed, case-insensitive) error

text — project content merely mentioning them is not a user stop. Longer,

tool-specific stop markers (cancelled: parallel tool call, `request

interrupted by user`, …) still match by containment.

  • **file_edit** stores the basename *and* the full path because the two answer

different questions. A hotspot ranking wants the basename — it is the name a

human recognises, and collapsing every route.ts into one row is the point.

The name is taken on either separator (core::path::basename): a

transcript spells paths the way the machine that wrote it does, and the same

file arrives both ways within one session. Cutting on / alone left a

backslash path standing in for the name and let one file compete against

itself for a hotspot slot, so the list ranked spellings rather than files.

Thrash detection wants the opposite: an episode claims *one agent kept retrying

this one file*, so it must distinguish two same-named files, and two sessions

editing one file in parallel. Keeping only the basename made those

indistinguishable and let stuck report parallel work as an agent stuck in a

loop. Detection therefore groups on (session_id, path) — the session implies

the project, and the path is unique within it (core::thrash). The deliberate

cost: thrash continuing across a resume or /clear splits into one episode per

session. A split under-reports a real burst; a merge invents one that never

happened, and the merge is what makes the report untrustworthy.

Surfaces that emit no event at all ― rule and claude_md ― never produce

rows here. That is expected, not missing data; surfaces.md classifies them as

catalog-only so their absence of events is never read as disuse. (Hooks used

to be on this list; firing became observable, so they emit hook_use.)

A span is an event with a duration window — currently skill_invocation.

The rest of this spec is mostly about spans, since that is where boundary and

attribution subtlety lives. Point events carry only an instant and their own

cost.

Span boundaries

A span starts at its invocation. It ends at the earliest of:

  1. the next human turn in the session;
  2. the next sibling invocation (an invocation that is not a child of this

span — see meta-skills below);

  1. a record following an idle gap longer than IDLE_GAP from the previous

record (active work has ended);

  1. the end of the session.

Rules 2–4 exist because rule 1 alone is insufficient. The naive definition

(end = next human turn only) let a span run to the end of the session whenever no

human turn followed, sweeping in unrelated tokens — observed: a doc-check span

absorbing ~580k output tokens of later, unrelated work. Rules 2 and 3 close the

span at the next real boundary; rule 4 bounds the trailing case. A span closed

only by rule 4 has a duration_sec that is a lower bound (the session may have

ended mid-work), so reports flag trailing spans rather than trusting their

wall-clock.

IDLE_GAP is a tuning constant injected into the core (not hard-wired), so

tests pin it.

Meta-skills and nesting ― intentionally flat (spike decision, PBI 22)

Some skills drive other skills (loop repeatedly invokes git-commit,

code-review, …). It is tempting to treat those inner calls as children of

the driver and nest them under a parent_id. We deliberately do not, and a

2026-11 design spike re-confirmed this against real transcripts instead of

reversing it:

Empirically, a meta-skill's "children" are recorded exactly like sequential

top-level commands: each appears as its own slash invocation with its **own

distinct promptId** — not the driver's, not a tool-path call, not a sidechain.

There is no structural marker (source, promptId, nesting depth) that

distinguishes "a skill loop ran" from "a skill the user ran next". Inferring

nesting would require a fragile time-window or a hard-coded list of meta-skills.

The spike checked every alternative against real transcripts and found each

one unsound or out of scope:

So the model stays flat: each invocation is its own span, and the boundary rules

(next human turn / next skill / idle gap) apply uniformly. This is not a loss of

accuracy — a child's cost is correctly attributed to the child (git-commit's

tokens land on git-commit); the driver's own small span reflects that it is an

orchestrator, not the place the work happened. Reports therefore never

double-count, and need no parent-inclusive/exclusive distinction.

The one thing that *is* attributable across the boundary is subagent cost, which

carries a real join key — see below.

Candidates the spike rejected, with reasons:

  • Time-window containment ("B's span inside A's span ⇒ nested"): sequential

siblings nest temporally too ― an agent running skill A over 1-10s and skill

B over 3-5s looks identical with or without nesting. Attributing on this

would corrupt the cost join the tool exists to keep honest.

  • Turn-boundary rule (no human turn between ⇒ nested): absence of a human

turn proves nothing; consecutive invocations in one assistant stretch are as

often sequential follow-ups as nested calls.

  • **parentUuid tree branches**: branches in real transcripts are attachment

records (hook results, file snapshots) riding alongside the next message ―

parallel metadata, not nested execution. The main line stays a chain.

  • Hard-coded meta-skill names: breaks on the first rename and can never

cover user-defined loops; the PBI itself flags this as irrecoverable.

Metrics

Each metric is computed from the records strictly within the event/span.

Metric Definition
out_tokens Sum of out_tokens over the span's assistant records. Each record carries only the output it is the first to report, so the sum counts every API response once however many records it was written as; see "One message, several records" below.
ctx_growth Compaction-safe context consumption: the sum of *positive* differences in prompt size between consecutive assistant records. Decreases (compaction, cache eviction) are clipped to zero.
ctx_start Prompt size at the span's first assistant record — *where this skill ran*, not where the session began. See "The session-start context is its own event" below.
ctx_peak Maximum prompt size across the span's assistant records.
duration_sec Last minus first record timestamp within the span. Zero when fewer than two timestamped records.
sub_tokens Tokens from subagents attributed to this span (below).
sub_agent_count Number of subagents attributed.
sub_tokens_estimated True when any attributed subagent was equally split (below).
model Representative model: the first assistant record whose model is not <synthetic>. NULL if none qualifies.

One message, several records

An assistant record is one transcript line, and one API response is written

as several lines whose usage objects repeat or accumulate the same output

(session-format.md). Summed naively, a response is charged once per line —

and the factor varies by skill (how often the model thinks before it acts), so

the error reorders skill rankings rather than merely inflating every figure.

The core does not see this. The adapter reconciles the lines of a response as

it parses, so each record's out_tokens is only the output that record is the

first to report; the core sums records exactly as the definition above says

and every response lands once. This keeps the layout knowledge where the

format-isolation rule wants it, and it also settles the boundary case: when a

span closes between two lines of one response (the response thought inside

one skill and then invoked the next), the output is charged to the span that

saw it first, never to both. Every line still yields a record, so

ctx_growth, ctx_start, ctx_peak and duration_sec see the same

timestamps and prompt sizes they always did.

Why ctx_growth, not max-minus-start

The intuitive "context consumed" is ctx_peak − ctx_start, but prompt size is

not monotonic: when a session compacts (observed ~1,000,000 → ~49,000 within one

file, marked by a compact_boundary record — session-format.md), ctx_peak

keeps crediting the pre-compaction peak long after that context was released, and

a span opening just after a peak can show a near-zero or negative figure. Summing

only the positive step-to-step increments counts what the span actually *added*

to the running context and is robust to mid-span compaction. ctx_start and

ctx_peak are stored alongside so the raw shape stays inspectable and

ctx_growth is auditable rather than opaque. The compact_boundary markers may

additionally be used to split or annotate a span; at minimum the metric must not

assume monotonic prompt size.

The session-start context is its own event

A span's ctx_start answers "how much context was loaded when this skill ran",

which is a *span* property. The always-on floor (surfaces.md) needs a different

question answered — "how much context did this session begin with" — and the two

diverge sharply: a session that only invokes a skill after a long conversation

has a span ctx_start in the hundreds of thousands while having started lean.

Minimising span ctx_start therefore does not converge on the floor; it converges

on whichever session happened to invoke a skill early.

So the session start is extracted separately, as one session_start event per

session carrying the prompt size of the session's first assistant record

(core::span::session_start_ctx). A transcript with no assistant record yields

no event — the session contributes no observation rather than a zero that would

sink every minimum it entered.

This remains a *lower bound* per observation: a resumed session's first record

already carries the restored context, so its start overstates a fresh one. Taking

the minimum across a project's sessions is what filters those out, which is why

the session count travels with the floor in reports — one observation cannot be

distinguished from one resumed session.

Subagent runs

A run is one execution of one agent type, extracted from its own transcript

plus the sidecar beside it (session-format.md). It is a first-class persisted

row (storage.md), not an intermediate, because the session-level total answers

only *how much* subagent work cost — never *whose*. Two agents with similar

spawn counts can differ by an order of magnitude in output, and the spawn count

alone cannot tell them apart; without runs, the largest figure in the report is

the one nothing can be done about.

A run carries the agent type, its own output tokens, its model, its depth in the

spawn tree, and the ids that link it back: its own tool_use_id, its parent

run, and the root tool_use_id its tree started at (core::subagent).

  • Every run counts once, at its own cost, whatever its depth. A nested run

is the agent that wrote those tokens; folding it into its parent's type would

bill an agent that only delegated. So the per-agent rows sum exactly to the

session-level total — for every session whose runs could be extracted. A

session analyzed before runs were extracted keeps its total, but once Claude

Code has pruned its transcripts its runs are gone for good, so a store can

hold rows for only part of its total; reports reconcile the two and label

the rows a partial split (core::subagent::SplitCoverage, cli.md's

reporting-honesty rules).

  • A run whose agent type is unknown (no sidecar) is kept, grouped under

"unknown". Dropping it would silently break that sum; guessing a type would

be worse.

  • The root link is what crosses the boundary. A nested run's own

tool_use_id names a call inside its *parent's* transcript, which no

main-thread span contains. Walking parent_agent_id to the tree's root gives

the one call the main thread actually made, so a subtree's cost lands on the

main-thread work that caused it. A broken chain (missing parent, or a cycle in

malformed input) leaves the run unrooted and unattributed rather than charged

to an arbitrary spawn.

Subagent attribution

A span's sub_tokens is the cost of the runs it spawned. The join is tried at

two precisions, and falls back only when it must:

  1. By spawn call. A run rooted at a known Agent call is attributed to the

one span whose window contains that call. Spans do not overlap, so this

claims at most one span: the attribution is exact and is never flagged

estimated.

  1. By turn. Used only when the run carries no call id at all — an older

transcript with no sidecar. Then only promptId is left, and it identifies

the turn rather than the spawn: the run is claimed by every span that spawned

anything in that turn, and when more than one competes they **split its tokens

equally** and are each marked sub_tokens_estimated. A single claimant is not

flagged: the flag means *this figure was split*, which is what the metrics

table above defines it as.

The precisions are selected by what the run *knows*, never by whether the exact

join happened to hit. Once a run carries a call id the turn join is never used

for it, in either failing case:

  • Its rooted call sits in no span. The root already says which call spawned

it, so no span containing that call means it was spawned outside every span.

  • Its parent chain is broken (a missing parent, or a cycle in malformed

input), so it has no root. The call id still shows it was spawned by another

subagent rather than from the main thread.

Retrying by turn in either case would charge the run to whichever unrelated span

happened to spawn something in the same turn — the exact error the call id

exists to prevent.

A run matching no span (spawned outside any skill, or unrooted) is not

attributed per-span; it still counts in the session-level total, which is exact

and needs no join.

Equal-split is a deliberate approximation — this tool ranks, it does not bill

(architecture.md) — and its worst-case error is bounded by the spread of the

competing runs' sizes. The flag, not false precision, is the mitigation, and it

now marks only the runs that genuinely could not be resolved.

The spawn event carries the run's cost

An agent_spawn event and a run describe one subagent from opposite sides: the

event is what the main thread *did*, the run is what it *cost*. They are joined

by the spawn call's id, so the event's out_tokens is the run's own output and

its sub_tokens the output of everything that run spawned in turn. A spawn

whose run is missing keeps zeros rather than borrowing another's figures.

This is why the spawn stays a point event rather than growing a window: its cost

is measured in the subagent's transcript, not inferred from main-thread records

inside a guessed boundary.

Per-span attribution is window-bounded, not authoritative

Attribution joins a subagent to the span whose window contains its Agent

spawn. Under the flat-span model a span's window can stretch past the skill's

own work (until the next human turn / skill / idle gap), so it can absorb

subagents spawned by *later, same-window* activity. Observed in real data: a

git-commit span — git-commit spawns no agents — picked up several agents

that ran after the commit in the same turn. There is no transcript marker for

"the skill returned", so this cannot be tightened structurally.

Joining by the spawn call instead of the turn does not fix this: the call is

inside the window either way, so the window is still the thing being trusted.

What it fixes is the *other* half — a span that spawned nothing in that turn no

longer takes a share.

Therefore events.sub_tokens is recorded per span (queryable, and exact for

skills that genuinely spawn their own agents) but is **not rolled up into the

per-skill report**, where it would over-count. The authoritative subagent figure

is the session-level total (sessions.sub_tokens), which is exact — every

subagent run counted once, no window guess involved — and the per-agent split of

that total (subagent_runs) is exact for the same reason wherever it exists.

The two are recorded separately, so the split can cover only part of the total

in a store that outlived the transcripts behind it; see the runs section above.

Determinism

The core takes the session's records plus tuning constants (IDLE_GAP) and

returns events with no hidden inputs — no clock reads, no randomness. Identical

records in always produce identical events out, so every rule above is pinned by

a fixture test.

a shared sessions dimension, the surfaces catalog, the events spine, and

ingested_files for incremental rebuilds. This spec defines the schema and the

ingest contract; the *meaning* of the columns lives in the specs that own them

(events.md, surfaces.md, config-format.md).

Indexes are the planner's choices

A declared index is an *option* the store hands SQLite's planner, not behavior:

it never changes what a query returns, only how the rows are reached. Indexes

are declared in INDEX_SCHEMA (store.rs) ― the DDL above mirrors it ― and

reconciled into every existing store on the next ReadWrite open, so adding one

is a non-migrating change: SCHEMA_VERSION does not move and no public API

changes. Only ReadWrite migrates, though: a ReadOnly open (--frozen /

sql) cannot create the index, so a store that has not been opened read-write

since it was declared keeps running its windowed queries as scans.

events_by_epoch (events(started_epoch)) backs the windowed readers that

scan events on started_epoch ― the twelve windowed methods over events,

including the rollup and skill-usage queries inside trend_aggregates' two

windows (2 x 4 queries; the session and subagent-total halves read the

sessions axis). The 2026-10-31 why-why bench (SQLite 3.54.0, a synthetic

fixture, a 7-day window) measured a 1M-row windowed query at 106-220ms without

the index and 36-42ms with it (about 3-5x), the plan changing from

SCAN events to SEARCH USING INDEX. The claim stops at the events axis:

the sessions-axis readers bind the TEXT sessions.started_at (the overhead

floors s.started_at) over a small table no index needs to serve, and the

per-agent breakdown binds subagent_runs.started_epoch, a different table the

new index does not cover.

The gain is not immediate: on a young store the planner keeps choosing

events_by_surface(surface_kind = ?), and this index pays off only as row

counts and statistics grow ― from roughly 500k-1M rows (at 1M rows, one trend

run costs about 500ms and findings about 1s, past the ~100ms felt threshold

per operation; row count via saniwalens sql "SELECT COUNT(*) FROM events").

Two scoping notes are the contract, not defects. The ingest delete

(DELETE FROM events WHERE source_path = ?) gains nothing from this index ―

serving source_path is a separate change of the same shape, not this one. And

the user-facing consequence of the ReadOnly asymmetry is stated where users

read it (cli.md's Period section, README's Notes).

Column encoding is defined once

The generic columns carry kind-specific meanings ― tool_error's friction

category rides in surface_id, its excerpt in source, the originating tool

in model; file_edit keeps the basename in surface_id and the full path in

target; a prompt's behavioral class rides in source. That mapping is

defined once, in EVENT_ENCODING (store.rs), and everything else derives

from it: the tool_errors view is generated from the table, the readers take

their column names from it (encoding_column), and the writer's INSERT

columns for tool_error and prompt are spelled from it too. The work-event

writer is the one place that fills physical columns without consulting the

table ― one statement spans several kinds, so the meaning a row's value carries

depends on its kind, which is read back through the table.

A new event kind is therefore a row in the table, not an edit scattered across

view SQL and queries: existing queries keep passing untouched, and the

round-trip tests (tool_errors_view_exposes_named_columns_and_project,

file_edits_carry_their_project_session_and_full_path, …) pin the writers

against the same table so writer and reader cannot disagree about which column

holds what.

The REFERENCES annotations above record which column joins which table; they

are not declared constraints. SQLite does not enforce foreign keys unless

PRAGMA foreign_keys is on, and turning it on would constrain the order a

delete-then-insert re-ingest may touch the tables in, for no integrity this

single-writer store does not already have ― so the schema states the

relationship and the ingest code maintains it (per source_path, below).

The store is also a read surface for arbitrary queries (cli.md: sql).

Because it is plain SQLite holding already-extracted facts, the session-analysis

slices a consumer might want ― the optimize agent chasing a root cause, say ―

are a SELECT away, which is cheaper and less error-prone than re-parsing the

raw transcripts. sql opens the db read-only

(Store::open(path, OpenMode::ReadOnly)) so an

ad-hoc query cannot mutate the derived store; views like tool_errors keep those

queries clean despite the column overloading.

attrs_json is the additive escape hatch: a new event kind or surface attribute

lands there without a migration, and graduates to a column only if reports query

it often. This is what keeps "add a new surface" a non-migrating change.

Prompt text is referenced, never copied

A prompt event stores (source_path, source_line), not the prompt string. The

future skill-extraction layer (clustering recurring prompts into candidate

skills ― architecture.md) recovers the text by re-reading that line on demand.

This keeps personal data out of the store (.claude/rules/session-data-privacy.md)

while reserving the capability now, so it survives transcript rotation: the

pointer is cheap to keep and the alternative ― discovering later that the text is

gone ― is unrecoverable. (If the source file is rotated away, the pointer simply

resolves to nothing; the event's counts remain.)

The store file is owner-only

What survives ingestion is still sensitive: file paths, tool-error excerpts,

project names, and pointers back into the raw transcripts. Since the default

store is a single well-known user-level path shared by every project

(cli.md), the umask default ― commonly a group/world-readable 0755

directory and 0644 file ― would expose that aggregate to other local

accounts. Store::open therefore creates the directory 0700 and the store

0600, matching how the optimize briefing (carrying the same class of data)

is written.

The store file is created by Store::open itself rather than chmod'ed after

SQLite creates it, which is what keeps the guarantee airtight: the schema write

would otherwise land in a file still carrying the umask mode, and SQLite copies

the database's mode onto the rollback journal it writes beside it, so the

journal inherits 0600 for free. An existing store is narrowed as well ―

a store an older saniwalens created under the umask is the case that actually

exists, and a permanently exposed one would mean this protection never reaches

anyone who already ran the tool. Only a regular file is re-moded, so a --db

pointing at a directory still fails at SQLite rather than being silently

re-moded, and a store owned by another account is left as it is ― re-moding it

is not this process's call, and refusing to run over it would break a store

legitimately created under another user.

Surface identity, scope, and the effective join

surfaces is keyed (kind, id, scope, project) because the same logical

surface can be installed globally and in any number of projects (e.g. a

git-commit skill in ~/.claude/skills/ and in two projects'

.claude/skills/). Events carry only (surface_kind, surface_id) ― the

transcript does not reveal which copy was loaded ― but they *do* join a session

whose project is known, and Claude Code's own resolution makes a project's

copy shadow the global one inside that project only.

So the catalog×usage join is defined per session project: an event from project

P joins P's project row for that (kind, id) when one exists, else the global

row. The join stays strictly 1:N-safe ― one event never matches two surface

rows, and one project's usage never inflates another project's copy

(Store::effective_catalog). Scope and project are retained on every catalog

row so reports can route a finding to the config layer that owns the fix

(cli.md --scope). surfaces.md and config-format.md describe the same

contract.

Timestamps are stored in UTC

started_at / started_epoch are UTC; the transcript gives UTC and the store

keeps it. Timezone is a presentation concern: the report converts to the

target zone (default JST) when bucketing and displaying (cli.md). Storing local

time would corrupt sorting and break portability across machines.

Project normalization

A worktree directory has its own cwd-slug (a ...--wt-feat-x suffix), so the

same logical project is otherwise scattered across slugs. sessions.project is

the normalized project (worktree suffix folded to the parent); sessions.slug

keeps the raw slug. Reports group by project so a project's usage is not split,

while the raw slug stays available for drill-down. The exact folding rule is an

adapter concern documented where it is implemented, but it must preserve a

testable invariant: **one logical project maps to exactly one project value,

and folding is idempotent** (folding an already-folded value is a no-op). Getting

this wrong splits or merges a project's usage, which is a correctness bug for

every per-project wedge, not a presentation detail.

sessions.root folds by the same rule one level down, on the real path rather

than the slug. The two must agree: the slug form keys on a --wt- infix and is

separator-free, so the path form accepts either separator ― otherwise a

worktree recorded on Windows folds by project while root stays split, and

per-root config scanning (config-format.md) sees two roots where there is one

checkout.

Schema evolution is non-destructive

The store outlives its inputs. Claude Code prunes transcripts on its own

retention schedule, and once a transcript is gone the rows extracted from it are

the only surviving record of that session ― nothing on disk can rebuild them.

So an upgrade may never resolve schema drift by asking for the file to be

deleted; Store::open migrates in place instead (migrate in store.rs).

The declared schema is the single source of truth for the target shape: it is

applied to a scratch in-memory database and read back through

PRAGMA table_info, and the live store is reconciled against that. Adding a

column to the declaration is therefore the whole of a routine migration ― there

is no parallel list of ALTER statements to keep in step, which is what made the

previous "detect a missing column, refuse the file" check drift into a

delete-and-lose-history instruction.

Drift is reconciled per object by what that object costs to lose:

  • sessions, events, ingested_files, meta hold history, so a missing

column is appended with ALTER TABLE ADD COLUMN. Existing rows take the

column's default, which the "report the gap, never substitute" contract below

already covers. A column that is already present is compared, not skipped ―

matching on name alone would pass silently over a retype or a changed default,

leaving the store permanently diverged from the declaration it is meant to

converge on.

  • surfaces is a snapshot of live config rebuilt on every analyze, so a shape

change drops and recreates it. The shape is compared first ― an unchanged

catalog must survive reopening, or a --frozen read would report an empty one.

When it *is* rebuilt, analyzed_at is cleared, so a --frozen read is routed

to the freshness warning instead of printing an ordinary header over an empty

catalog.

  • Indexes and views carry no data, so a drifted one is simply dropped and

recreated. Only a *drifted* one: CREATE INDEX / VIEW IF NOT EXISTS would keep

a stale definition ― a reader would then silently query yesterday's column

mapping ― but reindexing events on every open is not free either, so the

stored CREATE statement is compared against the declared one and matched

objects are left untouched. Objects the declaration does not name are also left

untouched: the store is meant to be explored with ad-hoc SQL, so a helper view

someone saved into the file is theirs to keep.

Indexes and views are declared apart from the tables, in their own constants,

and applied only after column reconciliation. Declared alongside the table they

would be replayed by the same execute_batch that creates missing tables, before

any column was added ― so an index over a column a future release introduces

would hit no such column on a legacy store and take the whole migration down,

which is the destructive refusal this design exists to remove. Deriving the names

to reconcile from the declaration is also what removes a hand-kept list: such a

list drifts, and a declared object missing from it would collide with its own

CREATE on the store's second open.

The whole migration runs in one transaction, as every other multi-statement write

here does: reconciliation can bail partway through, and a store left

half-migrated is the outcome in-place upgrading exists to avoid.

PRAGMA user_version carries SCHEMA_VERSION. Reconciliation only ever adds, so

routine additive changes do not bump it; it exists to catch what reconciliation

cannot express. A store stamped newer than this build is refused rather than

written to ― this build's shape would overwrite changes it does not understand,

in a file the newer binary still reads correctly. The version is also the seam

for a future change that reconciliation cannot cover (a column removed, retyped,

or given a new meaning). Reconciliation now *fails* on such drift rather than

ignoring it, so the seam cannot be skipped by accident; the migration written to

fill it must state what it discards, because the answer is no longer "nothing".

Store::open(path, OpenMode::ReadOnly) (the sql command) cannot migrate ―

the mode argument is the typed statement of which guarantee applies: ReadWrite

creates the file, narrows it to owner-only, and migrates in place; ReadOnly

does none of the three. An ad-hoc query against a store older than this build

surfaces SQLite's own missing-column error; any read command opens ReadWrite

and migrates first.

Incremental ingest

Transcripts are append-only and active sessions keep growing, so re-running

analyze must be cheap and idempotent.

One transcript, one batch

Store::ingest(IngestBatch) is the only way rows enter the store. A caller

submits everything one transcript yielded ― session meta, spans, usage events,

prompts, subagent runs, tool errors, work events ― and the store applies it in

one transaction, in its own order: the session row (insert-or-replace), the

delete of everything this file previously put in events, then each child set,

then the spawn-cost settle that reads the spawn events it just wrote. The order

the old five-function API demanded of its callers ― ingest_session first, or

its delete silently dropped the children ― is no longer a convention to

remember: no entry point expresses it. Re-ingest of the same file is the same

batch twice, which the replace contract below makes idempotent, and a batch's

atomicity means a failure mid-ingest leaves the previous rows intact rather

than a half-replaced file.

  • Before ingesting a file, compare (mtime, size) against ingested_files.

Unchanged → skip. Changed or new → re-ingest. mtime is **epoch

nanoseconds** (adapter::harness::file_fingerprint): whole-second

truncation made a same-second, same-size edit invisible, so the transcript

was skipped until something else moved the fingerprint. Epoch nanos fit in

an INTEGER until the year 2262.

  • Re-ingest is replace, not append: delete all events whose source_path

equals this file, then re-extract from the whole file and insert. This is why

events.source_path exists. Replacing avoids duplicate rows when a still-open

session is analyzed twice (the second pass simply supersedes the first).

subagent_runs replaces on the same key ― the parent transcript's path, not

the subagent's ― so one session's runs are rebuilt as a set, and a run whose

own transcript vanished does not survive as an orphan. The subagent files

themselves are deliberately not fingerprinted: a subagent's completion

appends its tool_result to the *main* transcript, so the parent's own

fingerprint already moves when a child finishes, and the next run re-reads the

whole directory. Stat-ing every file under subagents/ on every run would buy

only the case of a session killed between the child finishing and that

tool_result being written ― where the session's data is incomplete anyway. Filling an

agent_spawn row's cost from those runs is scoped to that same key: a call id

is unique within a session, and nothing guarantees it across sessions

(a resumed or copied transcript can carry one over), so an unscoped join would

pick an arbitrary row and sum another session's runs on top.

  • surfaces is rebuilt wholesale on each run from current config ― the catalog

is a snapshot of *now*, not an accumulation. (Usage is historical; catalog is

current ― surfaces.md.)

The fingerprint is keyed on the *file*, not on what saniwalens knew how to extract

from it. On its own that skip never expires: a session that has closed will never

change again, so its rows would stay pinned to whatever the saniwalens that first read

them understood ― an event kind added later stays missing for that session, a

field added later stays NULL, and a classifier that learned a new pattern never

reaches it.

meta.analyzer_version is the invalidation. It names the analysis semantics

the stored rows were produced by; a run whose version differs from the store's

ignores the fingerprint skip, re-ingests every transcript once (replace, per

above, so this is safe to repeat), and stamps the new value. Bump it whenever

extraction or classification changes what an *unchanged* transcript yields. It is

deliberately not the crate version ― a release that changes no analysis should not

cost every user a full re-analyze. The Claude Code pair lives with its mapping in

adapter::transcript (CLAUDE_ANALYZER_META_KEY / CLAUDE_ANALYZER_VERSION);

each other harness carries its own beside its own mapping (harness.md), and

Store::is_analyzer_current(key, version) compares whatever it is handed ― the

store owns no harness's key.

Invalidation only recovers what the transcript actually holds. Where a signal was

never recorded at all, the contract remains that a reader **reports the gap or

drops the row**, never substitutes something plausible:

  • overhead reports the always-on floor as unavailable when no session_start

was observed, rather than falling back to a skill span's ctx_start

(surfaces.md).

  • Thrash detection excludes file_edit rows with no target, rather than

falling back to the basename in surface_id (events.md).

Both fallbacks would have looked like working output while silently restoring the

bug the field exists to prevent, which is worse than an empty report. Such a

result is a fact about the input: re-analyzing will not conjure a signal the

transcript never recorded, and the transcript it came from may be gone entirely.

(mtime, size) is a cheap change detector, not a content hash; a touch that

changes mtime without changing bytes triggers a harmless idempotent replace, and

any byte change moves size or mtime. A content hash is a later hardening option

if the cheap detector proves insufficient.

The nanos unit itself is a fingerprint change: mtime values stamped in whole

seconds never match an epoch-nanos reading, so the first run after the upgrade

re-ingests every file-backed transcript once (replace, per above, so this is

safe to repeat) and then the skip resumes. No analyzer_version bump is

involved ― row-backed fingerprints (opencode's time_updated_ms plus message

count) keep matching, so only the file-backed paths (Claude Code transcripts,

kilocode's two-file task fold) pay the one-time pass. The stat-before-read

rule below is unchanged: a file that grows mid-run still shows a mismatch next

run, because the recorded size is the bytes actually consumed.

Reading files that grow mid-run

Active sessions are appended to while analyze runs, so the reader must tolerate

a torn read: a partial final line is skipped (JSONL append is not atomic at

line granularity), never parsed as a broken record. The fingerprint stored in

ingested_files is captured after the read completes ― recording the size

actually consumed. A file that grew during the read therefore shows a changed

(mtime, size) on the next run and is re-ingested, picking up the tail. Stamping

the fingerprint before the read would record the post-growth size against

pre-growth events and permanently skip the tail. The stamp is additionally gated

on a post-read re-stat (restat_matches in adapter::harness): only when the

re-read fingerprint equals the pre-read one is the stamp written, so a mid-run

append fails closed to "ingest without stamping" and the next run re-ingests

rather than skipping on a stale stamp. Row-backed fingerprints (opencode's

time_updated_ms plus message count, kilocode's task fold) re-query after ingest

under the same gate.

Why a dimension + catalog + spine, not one span table

An earlier design had a single skill-centric spans table. It could not hold

rules, hooks, MCP, or prompts without contortion, and it conflated the catalog

(what is installed) with usage (what ran). Splitting into sessions (dimension)

+ surfaces (catalog) + events (usage) lets every configuration surface share

one usage spine and one catalog shape, and makes the optimization analysis a

join rather than a special case per surface ― see surfaces.md.

subagent_runs sits beside the spine rather than in it because a run is not an

event *of the session* ― it happened in another transcript, on another thread,

and its cost was measured there. Putting it in events with `surface_kind =

'agent'` would double-count every spawn in the catalog×usage join, which counts

rows per surface. The spine keeps the main thread's spawn; the run keeps the

cost; events.target joins them.

Harness Specification

saniwalens analyzes sessions from more than one agent harness (Claude Code,

opencode, kilocode). This spec owns the harness contract:

how the CLI selects a harness, where each harness's input and store live, and

what each harness can and cannot report in v1. The per-harness *formats* live

in their own specs (session-format.md, session-format-opencode.md); the

*analysis semantics* stay shared (events.md, surfaces.md).

One store per harness

Stores are never shared across harnesses. Each harness gets its own SQLite

file holding a single harness's sessions, so the Claude Code path ― behavior,

defaults, and existing stores ― is untouched by every later harness:

Harness Default store (--db)
claude ${XDG_STATE_HOME:-~/.local/state}/saniwalens/saniwalens.db (unchanged)
opencode same state dir, saniwalens-opencode.db
kilocode same state dir, saniwalens-kilocode.db

An explicit --db always wins, exactly as before. The schema is identical in

every store (storage.md); only the rows' origin differs, which is why no

harness column exists ― a file holding one harness needs no per-row label,

and a shared file is what this design refuses to create. No cross-harness

aggregation exists in v1.

Every store records its harness in meta (`harness = claude | opencode |

kilocode`).

A command reading a store built by another harness refuses with a hint

naming the expected --harness (or a matching --db), rather than reporting

one harness's rows as another's. sql enforces the same guard: it resolves

its default --db through --harness, so saniwalens --harness opencode sql

lands on the opencode store without flags.

--harness

A global flag, default claude:


saniwalens [--harness claude|opencode|kilocode] <command>
  • The default keeps every existing invocation byte-identical in behavior ―

this is what keeps the change upstream-mergeable.

  • There is deliberately **no auto**: detection order across harnesses would

be ambiguous (several harnesses installed, several stores present), and an

ambiguous default misattributes rows silently. Explicitness is the whole

point of separate stores.

  • Unknown values fail with the valid list.

--projects keeps its meaning ("input root") but resolves per harness:

a directory for Claude Code ($CLAUDE_CONFIG_DIR/projects), the opencode

database file for opencode (default ~/.local/share/opencode/opencode.db),

and the kilocode tasks directory for kilocode ― default the **first existing

editor globalStorage candidate** (kilocode_tasks_candidates), since the

path varies with the editor install (Code / Cursor / VSCodium) and the

platform, so the candidate list, not one hardcoded path, is the contract.

The resolved root is recorded in meta (projects_dir) and reused by the

read commands' auto-refresh, unchanged plumbing carrying a new value.

opencode analyze (v1 capability)

--harness opencode analyze reads the opencode database read-only and

ingests it into the opencode store. The mapping itself is

adapter::opencode (session-format-opencode.md); this section is the shell

contract:

  • Sessions come from the session table in time_created order.

project is the session's directory verbatim (real paths need no slug

recovery), root is the same directory, slug is opencode's own slug,

and the ingest delete-key (source_path) is opencode:<session-id>.

  • Incremental ingest is per session, keyed opencode:<session-id> with

(mtime = session.time_updated, size = message count). A whole-file

fingerprint would re-ingest every session on each run (opencode appends

constantly); per-session keys skip what did not move. Replace semantics

make re-ingest idempotent, as for Claude Code transcripts.

  • Invalidation has its own version key. The shared ANALYZER_VERSION

would force Claude Code users through a full re-analyze on every

opencode-only extraction change, so opencode rows stamp

meta.opencode_analyzer_version instead

(adapter::opencode::OPENCODE_ANALYZER_VERSION). Bump it under the same

rule: whenever opencode extraction changes what an unchanged database

yields.

  • Subagent runs are not ingested. opencode has no subagent-side

transcripts, so sub_tokens/sub_agent_count stay zero and the per-agent

split is empty. SplitCoverage::is_unavailable requires a positive total,

so no misleading "run analyze to fill it" warning fires ― zero subagent

activity reads as zero, which is what it is.

  • Prompts are not ingested in v1. The store's prompt pointer is a

(source_path, source_line) file coordinate (storage.md); opencode text

lives in database rows, so the pointer needs a new encoding. Until then the

prompts view is empty under opencode ― reported as empty, never

fabricated.

  • Permission denials count zero. No runtime denial marker was found in

the opencode format, and no heuristic stands in for one.

  • The surface catalog covers commands, agents, and `AGENTS.md. Global

command/ and agent/ come from the opencode config root; each known

project root contributes its .opencode/ pair plus AGENTS.md (with

@imports). Skills, MCP servers, and permissions stay out until their

definition sites and usage joins are both observed

(config-format-opencode.md); live Skill usage meanwhile shows as

orphaned rows in inventory, which is the honest signal that a catalog

site is missing.

  • meta.config_dir is recorded empty: no config was scanned. (An empty

value, not a missing key, so readers can distinguish "nothing scanned"

from "unknown".)

kilocode analyze (v1 capability)

--harness kilocode analyze reads each task directory's two JSON files

read-only and ingests it into the kilocode store. The mapping itself is

adapter::kilocode (session-format-kilocode.md); this section is the shell

contract:

  • Sessions come from the task directories under the resolved input root,

sorted for a deterministic order. A directory without both

api_conversation_history.json and ui_messages.json is not a session and

is skipped. One task directory is one saniwalens session; the task uuid is both

the session id and the slug.

  • The project root is a stated heuristic (estimate_root): the common

parent directory of the leading tool paths, since kilocode stamps no

cwd anywhere. A task whose tools name no absolute path stays unrooted ―

empty, never guessed.

  • Per-task ingest keys. kilocode:<task-uuid> keys each task, with

(mtime = the later of the two files', size = their summed length) as the

fingerprint ― either file moves on activity, and the directory stat would

re-ingest every task on each run (checkpoints move too). Replace semantics

make re-ingest idempotent, as for the other harnesses.

  • Invalidation has its own version key, meta.kilocode_analyzer_version

(adapter::kilocode::KILOCODE_ANALYZER_VERSION), for the same reason the

opencode rows carry theirs: a kilocode-only extraction change must never

force other harnesses through a full re-analyze.

  • Subagent runs, prompts, and permission denials are not ingested. No

spawn marker, no usable prompt pointer (the store's `(source_path,

source_line)` coordinate has no line meaning in JSON), and no denial marker

was measured in the kilocode format ― the counts stay zero and the views

read as empty, which is what they are.

  • The surface catalog is empty. The global ~/.config/kilo sites are

measured (commands, skills, kilo.json) but not cataloged yet ― the config

half is a separate spec and change. inventory says so instead of showing

a table that looks like an empty config, and meta.config_dir is recorded

empty (nothing scanned, distinguishable from unknown).

optimize under opencode

The briefing composes from the store either way, so --print works under

every harness. Launching runs the harness's own agent on a data-free pointer

prompt (the briefing travels via a private temp file, as for Claude Code):

claude <prompt> opens interactively, while `opencode run --format json

--title 'saniwalens optimize' <prompt>` runs the advisor headless ― no user is

present for the approval gate, so the headless instructions

(run_instructions) make the printed plan the final output and forbid

edits.

The headless terminal stays quiet: saniwalens reads the JSON event stream line

by line and surfaces only what the agent says ― text parts (narration, then

the plan) on stdout, one-line tool markers on stderr ― while every raw line

and the child's stderr go to a private (0600) log file whose path is

printed up front. A successful run removes the log (the raw stream may echo

secrets); SANIWALENS_KEEP_RUN_LOG=1 keeps it for post-mortem inspection.

Rendering is lenient (the upstream event shapes are

unversioned): a line with no recognizable text stays in the log, and a run

that renders nothing readable says so instead of leaving silence. Every exit

from the run ― success, a failed read, a failed spawn, or a failed wait ―

stops the beat and reaps the child; a failure keeps the log and is reported

with the raw log's

path so the full output is still reachable (cli/headless.rs).

--timeout <DURATION> bounds the wait; on expiry the child is killed and reaped

and the error names the raw log. A grandchild that outlives the direct child can

keep the pipe open: the reader is detached on timeout so the command still

returns promptly, and the residual process is a known limitation.

--verbose inherits stdio for the raw streaming instead.

Under kilocode the briefing composes from the store either way, so --print

works. Launching opens an interactive kilo session on the pointer prompt ―

kilo --prompt <prompt>, the experience the claude launch gives: the user is

present to approve the briefing read (kilo gates every tool call where

opencode does not, so a headless run would need --auto instead), steer the

investigation, and apply the fixes themselves. A bare kilo <text> positional

is treated as a file to open (measured), not a prompt ― --prompt is the

TUI's message surface.

The launch shape itself is per-harness data on the seam:

Harness::launch_command (adapter::harness) returns the binary, the

leading argv, and the run mode beside the harness's other facts

(input_unit, db_file_name), so a new harness lands as one arm there and

the shell's launch side (cli/mod.rs) neither matches nor changes ― the same

contract the analyze seam keeps (Harness::analyze).

The headless raw stream renders through per-harness data on the seam too:

Harness::run_line_renderer (adapter::harness) returns the adapter fn that

turns one raw line into a RunEvent beside the launch shape, and the

delivery plan carries it to run_headless, so the cli/headless.rs logged loop

receives the seam's choice instead of naming a module. Rendering stays lenient

either way (the upstream event shapes are unversioned). Claude's launch opens

interactively, so it has no headless renderer; kilo is an OpenCode fork and

shares the event stream, so a headless kilo run is the same arm ― still gated

on --auto by the launch shape above. The quiet-stretch logic the loop leans

on lives in one place too (heartbeat, cli/heartbeat.rs), so the due

decision is a pure function and the beat model in its tests drives the same

decision as the spawn. What the seam's test pins is the sample sequence and

the stop, not the spacing: a beat carries the count it reads when it fires (0

before any event streams, then the count at that moment), and after stop

flips the thread exits and the receiver disconnects. The wall-clock spacing

between emitted beats is not observed by a test (the pure decision's spacing

is pinned by cli::heartbeat unit tests). At most one beat is sent between

the flag being set and the second stop check observing it: a structural

invariant of the loop's two checks, not an observed quantity ― a beat queued

before the stop is indistinguishable from one sent after it.

CADENCE (30s) is the minimum scheduled spacing between beats and POLL (500ms) is how

often the thread wakes to re-check stop and to see whether the next beat is

due. A beat fires when the observed elapsed time reaches its deadline, and the

following deadline is then counted one cadence from that observation, not from

the old deadline: the slots a stall swallowed (a process freeze, a blocked

stderr) are dropped rather than replayed, so the resume shows one beat and the

next one waits a full cadence instead of a back-to-back burst. The phase is not

anchored to the start, and because the loop only looks after each poll, a

cadence shorter than the poll is degenerate and beats on the poll, not on the

cadence. Beat rejects a zero cadence or a zero poll at construction, so the

test seam cannot silently turn into a tight loop or a per-poll beat.

Copy that attributes rows to a harness uses Harness display helpers, so

opencode output never claims to be Claude Code's:

the prompts framing; the stuck/thrash lines say "the agent" (neutral

for both harnesses).

  • instruction_file / project_config_ref / global_config_ref wherever a

finding routes to the config layer owning the fix (doctor, failures,

  • The optimize briefing and advisor instructions render from a

HarnessCopy (core::optimize), plain data the shell assembles from the

  • Freshness lines count the harness's own unit (transcript(s) vs

Static --help texts still describe the Claude Code defaults; per-harness

The analyze seam ― Harness::analyze

analyze is dispatched exactly once, on the harness:

  • Harness::analyze (adapter::harness) is the only dispatch. Each arm calls

the matching adapter module's analyze (adapter::claude,

adapter::opencode, adapter::kilocode), which owns input discovery,

fingerprint skipping, extraction wiring, and the store hand-off for that

harness. The shell guards the store against a cross-harness write and then

  • Each harness's analyzer-version key sits beside its mapping ―

adapter::transcript::CLAUDE_ANALYZER_META_KEY / CLAUDE_ANALYZER_VERSION,

store.rs and a new harness adds its own without touching the store.

gates roots on disk. Each harness contributes only its site rows

(global_sites / project_sites: a path plus a loader), so a new config

site or surface kind is data, not a traversal edit

(config-format.md).

Forward compatibility

A new harness adds: a Harness variant, its default input root and store

name here, its format spec, and an adapter module carrying its analyze routine

behind Harness::analyze ― input route, fingerprinting, and its

analyzer-version key included. Its launch shape rides the same seam:

(guard_harness in session.rs, invoked from run_analyze), and a new

harness passes it unchanged; every other per-harness fact reaches the shell

as seam data. Nothing in the Claude Code path moves ― that immobility is the

contract this spec protects.

next candidate, tracked as a contribution, not a committed release item. See

CONTRIBUTING.md for what a new-harness proposal must bring (observable

transcript and config formats, OSS-reproducible fixtures).

Session Format Specification

This spec catalogues what the adapter layer knows about the Claude Code

transcript format ― the usage half of the catalog×usage model

(architecture.md). Its sibling config-format.md covers the config half. Only

the adapter may use the field names below; everything downstream sees the

internal domain model (.claude/rules/format-isolation.md). This is one of the

two specs most likely to change when Claude Code ships a new release.

Observed against a real ~/.claude/projects/ tree (≒460 transcript files)

on 2026-06-14, Claude Code transcript version 2.1.x. Counts drift as

sessions accumulate; the shapes are what matter.

File layout


~/.claude/projects/


  <cwd-slug>/


    <sessionId>.jsonl                          ← main session transcript


    <sessionId>/subagents/


      agent-<agentId>.jsonl                    ← one transcript per spawned subagent


      agent-<agentId>.meta.json                ← that subagent's sidecar (below)
  • <cwd-slug> encodes the working directory (path separators → -). Worktree

directories appear as their own slugs (e.g. a ...--wt-feat-x suffix); the

store folds these to a parent project ― see storage.md.

  • The slug is lossy (- in a path component is indistinguishable from a

separator), so the real project root comes from the records themselves: most

record types carry a cwd field with the absolute working directory. A

session that changes directory stamps later records with the child path, so

the adapter takes the first recorded cwd as the session root

(session_cwd in adapter/transcript.rs) ― the directory the session

started in, which is what the slug encodes. Sessions whose records carry no

cwd have an unknown root; project-config scanning simply skips them

(config-format.md).

  • A main transcript and its subagent transcripts are separate files.

This separation is load-bearing: a main transcript's records describe only the

main thread's context, so main-thread metrics are computed from the main file

alone, uncontaminated by subagent work.

Each file is JSONL ― one JSON object per line, appended over the session's life.

Records the adapter reads

Records carry a type. The adapter takes the listed fields and ignores the

rest; unknown types are skipped.

assistant ― the source of all runtime cost

  • timestamp ― ISO-8601, millisecond precision, UTC (Z suffix, e.g.

2026-05-14T22:40:06.133Z). Parsed to a UTC instant; timezone presentation

happens later (cli.md).

  • message.id ― the API response id. One response is written as **several

lines, one per content block** (thinking, text, tool_use), and every

line repeats message.model and carries a message.usage; the id is what

ties them back to one response. The lines take two shapes: on the main

thread each line's output_tokens is the response's final value repeated;

in a subagent transcript it is a running total that only grows, the last

line carrying the whole response. The adapter reconciles both at parse time

by emitting, per line, only the output not yet reported under that id ― the

whole value on the first line and zero on a repeat, or each step of a

running total (adapter::transcript::assistant_records). That is the

per-id maximum, spread over the lines that first observed it, so the core

can sum records and count each response once (events.md). Keeping the

*first* line's value instead would under-count subagents badly, and

stop_reason is no substitute: every main-thread line carries one, and some

subagent responses carry it on no line. A line with no id reports its value

as is.

  • message.model ― e.g. claude-opus-4-7. May be the sentinel <synthetic>

for locally-generated turns; excluded when choosing an event's representative

model (events.md).

  • message.usage ― token accounting: input_tokens,

cache_read_input_tokens, cache_creation_input_tokens, output_tokens.

  • Prompt size at a request (the full context handed to the model) is

input_tokens + cache_read_input_tokens + cache_creation_input_tokens. It

is not monotonic: at the context limit Claude Code compacts and the next

request's prompt size drops sharply (observed ~1,000,000 → ~49,000). The

context metric is defined to survive this (events.md).

  • message.content[] ― blocks; the adapter inspects tool_use blocks for skill

invocations, subagent spawns, and tool usage (below).

user ― human turns and slash invocations

  • A human turn is a user record that is not isMeta and whose content is

real input (not solely a tool_result). Human turns delimit event ends

(events.md).

  • A slash-command invocation appears as <command-name>/NAME</command-name>

in the content.

system ― structural signals

system records carry a subtype. Several are directly useful:

subtype Use
compact_boundary Marks a context compaction structurally ― so the context metric detects compaction from the boundary record, not by guessing from a token drop.
turn_duration A measured turn wall-clock, usable for duration cross-checks.
local_command A slash command run locally (carries its own <command-name>).
away_summary, compact_boundary, scheduled_task_fire, … Other lifecycle markers; read as needed.

Usage signals the adapter extracts

The transcript yields events of several kinds (see events.md for how each

becomes an event). The adapter recognises at least:

Signal Where in the transcript
Skill invocation ― slash <command-name>/NAME</command-name> in a user (or system local_command) record
Skill invocation ― tool assistant tool_use with name == "Skill", input.skill == NAME
Subagent spawn assistant tool_use with name == "Agent"
Tool use assistant tool_use blocks (built-in and MCP tools, by name)
User prompt user human turns (not last-prompt, which is a single leaf-pointer to the latest prompt ― one per region, not per turn)
Tool failure a tool_result block flagged is_error or wrapping <tool_use_error>. Categorised from the entry's toolDenialKind where that marker can be attributed to it (below), else from the text (core::friction); a short readable excerpt is kept. Linking the result's tool_use_id to the assistant tool_use block recovers both the originating tool and the call's target (its input.file_path / command) ― so a report shows which tool produced each failure and which file/command it hit, even when the error text omits the path (e.g. edit-precondition names no file)
Permission denial toolDenialKind on the entry that carries the denied tool_result, else the denial text inside it ("Permission for this action was denied"). Structural where the marker is present; a low-confidence heuristic where it is not ― see note below
Compaction system subtype == compact_boundary

These map to configuration surfaces (surfaces.md): a Skill invocation to a

skill surface, an MCP tool_use to an mcp_tool/mcp_server surface, and so

on. New surface kinds are added by recognising new signals here ― additively,

without disturbing existing extraction.

Detection is structural, not substring. A skill invocation is a real

tool_use block (name == "Skill") or a <command-name> in an actual

user/local_command command field ― never a <command-name> or Skill

string appearing anywhere in content. Quoted text (a transcript that discusses

skills, a prompt containing the literal tags) must not be mis-read as an

invocation. The adapter matches on record structure and field position.

Not every surface emits a usage signal. rule, hook, and claude_md have

no discrete invocation in the transcript ― they are injected context, not

events. They appear in the catalog (config-format.md) but acquire no events;

surfaces.md classifies surface kinds as usage-measurable vs catalog-only so the

join does not mistake "no event possible" for "unused". The permission-denial

signal above is the one partly heuristic signal, and is flagged as

lower-confidence wherever it is used.

Why a denial is read from its marker, not its words

A denied call carries toolDenialKind ― permission-rule, user-rejected,

automode-blocked ― on the entry, one level above the tool_result block it

explains. Reading it is not an optimization but the only reliable route: the text

below a hook denial is written by the user's own hook, so its wording and its

*language* are arbitrary, and no keyword list can converge on it. The marker is

upstream's fixed vocabulary, so it classifies a denial identically whatever the

hook chose to say. permission-rule and automode-blocked are blocks the user's

config could relax; user-rejected is the user answering no.

The field is optional in both directions: older transcripts predate it, and not

every refusal carries one (a built-in guard may simply return an error). An

unrecognised kind falls through to the text classifier rather than overriding it,

so a kind added upstream degrades to today's behavior instead of erasing it.

The marker is scoped to the entry, not to a block, so it is only attributed

when the entry holds exactly one failed tool_result ― every transcript observed

writes one per entry. Were upstream to batch several, a shared marker could not

say which of them it denied, so it is dropped and the text classifier decides for

all. Both fallbacks follow the same rule: where the marker cannot be attributed

with certainty, it does not get to assert anything.

Skill invocation has two distinct paths

slash (the human typed it) and tool (the model invoked it) are **not

duplicates of one event** ― empirically a slash is not shadowed by a matching

tool call. The adapter emits both, tagged with their source; the core does

not deduplicate them.

Subagent linkage

Subagent cost is attributed back to the event that spawned the work, but a

subagent's tokens live in a separate file, and its own transcript never names

the agent type that ran. Both facts come from the sidecar; promptId is the

fallback when there is none.

Each agent-<agentId>.jsonl has a sibling agent-<agentId>.meta.json:

Field Use
agentType The agent that ran (Explore, a custom agent's name) ― the only place it appears. Without it a run's cost cannot be attributed to a type at all.
toolUseId The id of the Agent tool_use block that spawned this run ― an exact join to one spawn.
parentAgentId For a subagent spawned by a subagent, the parent's agentId. Absent at depth 1.
spawnDepth 1 for a main-thread spawn, 2+ for a nested one.
model The model the run used.

The transcript side of the same join:

  • A subagent transcript's records carry agentId, sessionId, and promptId;

the file is agent-<agentId>.jsonl.

  • The same promptId appears on the parent session's records for the spawning

turn. It is inherited by the whole subagent tree, so a nested run's

promptId is still the top-level turn's ― it identifies the turn, never the

spawn.

  • Several subagents share one promptId (parallel spawn, and every nested run),

so promptId alone makes per-event attribution approximate. toolUseId does

not: it names one call. The adapter therefore keeps the Agent block's id

on the spawn record and prefers that join, falling back to promptId only

when a sidecar is missing ― see events.md.

Nested runs exist only here. An agent spawned by an agent has no Agent

tool_use anywhere in the main transcript, so the main thread's spawn count is

not the number of subagent runs; the subagents/ directory is. Observed on a

real tree: roughly half of all runs were nested, and one agent type ran seven

times more often than the main transcript alone suggested.

The sidecar was observed on transcript versions 2.1.220-2.1.246, present

for every subagent transcript in the tree. Earlier releases may not write it,

so every field is read as optional and an absent sidecar degrades to the

promptId join with an unknown agent type ― never to a guessed one.

Subagents do not invoke skills

Empirically, subagent transcripts contain no Skill tool_use and no

<command-name> ― subagents are not given the Skill tool. So every skill

invocation originates in a main transcript; subagent files are read only to

attribute tokens to the main-thread event that spawned them. If a future

release gives subagents skills, this assumption is the first thing to revisit.

Session Format Specification — opencode

This spec catalogues what the adapter layer knows about the **opencode

session** format — the usage half for the opencode harness. Its Claude Code

sibling is session-format.md; the two specs share the same downstream

contract (the internal domain model, core::span::Record) but describe

different upstream shapes. Only the adapter may use the field names below

(.claude/rules/format-isolation.md). The opencode store is separate from

the Claude Code store (one DB per harness), so nothing here constrains the

Claude Code mapping, and vice versa.

Observed against a real ~/.local/share/opencode/opencode.db (opencode

1.x, SQLite via drizzle) plus its file mirror under

project/global/storage/session/. Counts drift as sessions accumulate; the

shapes are what matter. The database is the source of record — the file

mirror carries the same content and is not read.

Where sessions live


-- ~/.local/share/opencode/opencode.db


session(id, project_id, directory, title, agent, model,


        tokens_input, tokens_output, cost, time_created, time_updated, ...)


message(id, session_id, time_created, time_updated, data JSON)


part(id, message_id, session_id, time_created, time_updated, data JSON)
  • session.directory is the real working directory — no lossy slug

encoding, so unlike Claude Code there is nothing to recover from record

fields. Project-config scanning walks these directories directly.

  • All timestamps are milliseconds since the Unix epoch (13 digits), UTC.

message.time_created orders the transcript; part rows carry their own

state.time{start,end} where the tool ran.

  • message.data and part.data are JSON blobs. The adapter reads only the

fields below and ignores the rest; unknown type values are skipped.

Records the adapter reads

message — one row per turn

data.role is user or assistant.

Assistant (role == assistant) carries the whole turn's cost in one place:

  • data.tokens{input, output, reasoning, cache{read, write}} — verified

identical to the same message's step-finish part (`total ==

input+output+reasoning), and at most one step-finish` part exists per

message. So message-level tokens are authoritative and the adapter never

sums step-finish rows — there is no multi-line repetition to reconcile

(the Claude Code message.id problem does not exist here).

  • data.modelID (e.g. preview/GLM-5.3-Flash) — the representative model.

Absent → "unknown" (honest, never a guess).

  • data.agent / data.mode (e.g. build) — the running agent.
  • data.path{cwd, root} — per-message working directory (informational; the

session root comes from session.directory).

  • data.error{name, data{message, statusCode, ...}} — a failed request

(e.g. provider APIError). Still yields its record with whatever tokens it

carries (usually zero); the error half is friction input, not a reason to

drop the row.

  • data.parentID — the reply-chain link. Used as the coarse spawn key

(below), the way promptId is for Claude Code.

User (role == user) rows hold part children of type text (the prompt)

and file (attachments). A user message yields a HumanTurn **only when it

has a text or file part** — compaction parts also hang under user

messages and must not delimit spans.

session.title is a generated summary, not a prompt — never read as one.

part — one row per content block or tool call

data.type decides the mapping:

type Mapping
text (under user message) part of the human turn (prompt material)
text / reasoning (under assistant message) display only — cost already on the message row; no record
tool with tool == "skill" SkillInvocation{skill: input.name, source: Tool}
tool with tool == "task" AgentSpawn{agent: input.subagent_type, tool_use_id: callID, prompt_id: message.parentID}
tool with any other tool ToolUse{tool} (observed: read, bash, edit, write, glob, grep, todowrite, question, webfetch, …)
tool with tool == "skill_use" ignored — this loads skills into context (input.skill_names), it is not an invocation. Counting it would double-count tool == "skill" rows
type == "subtask" ignored (child-side mirror) — carries {agent, command, model, prompt} for a spawn whose parent-side task part already emitted the AgentSpawn. Emitting both would double-count agent usage
type == "step-start" / "step-finish" structural/cost echo — message tokens already counted; no record
type == "compaction" compaction marker ({auto, overflow, tail_start_id}); the context metric is compaction-safe without it (events.md); no record
type == "file" attachment pointer; no record

Record order within a session is message.time_created (ties broken by

message.id), and within a message the part-derived records come before

that message's Assistant cost record — so a skill span opens at the

invocation and includes the calling turn's cost, mirroring the Claude Code

adapter's ordering. The cost record is stamped with the turn's *end* (the

latest part time, falling back to the message time): tools run after their

message is created, so stamping the creation time would invert the stream and

produce negative span durations. Part timestamps use state.time.start,

falling back to the owning message's time_created.

Subagent linkage (per-run costs since PBI 16)

A task spawn is exact on the parent side (callID). opencode runs

subagents in-session, so there is no sidecar transcript — but each task

tool part names the run's own session in state.metadata.sessionId, and

that id joins session.id. A part whose sessionId matches a session in

the snapshot becomes one subagent_runs row: agent type from

input.subagent_type, the parent's callID as the join key both sides

share (tool_use_id and root_tool_use_id), the model from

state.metadata.model.modelID, and out_tokens summed from the child

session's own assistant cost rows. The row's locator is

opencode:<child session id> — there is no per-run transcript file, so the

child session id (joinable back to sessions.id) stands in for the sidecar

path a Claude Code run would carry. Spawns count agent-surface usage as

before; this only adds the run rows.

Attribution reuses the shared join (core::usage::attribute_subagents):

runs are built per parent session and matched only against that session's

spans, so a callID that repeats in another session can never misattribute

— the scoping the storage join contract requires. Parts that name no

session, or a session outside the snapshot, keep the old behavior: no run is

written, and the session totals still carry the spend. Nested spawns (a

task part inside a child session) write their own depth-1 rows and stay

unattributed until the nesting join exists. OPENCODE_ANALYZER_VERSION

bumped with the change, so stores refresh through a full re-ingest once.

What is deliberately not mapped (v1)

  • Slash-command invocations typed by the human (/review etc.) — user text

has no structural command wrapper (unlike Claude Code's <command-name>),

and substring-matching prompts would misread prose discussing commands.

  • skill_use and subtask parts (above) — context loading and child-side

mirrors, not invocations.

  • data.cost (per message, per step-finish) — billing-adjacent and

provider-specific; counts are usage signals for ranking, not a ledger

(architecture.md).

  • Config surfaces (opencode.json, commands, agents, MCP) — the catalog half

is a separate spec (config-format-opencode.md, not yet written) and a

separate change.

Read only the fields above; ignore unknown type/tool values and missing

mistake worth counting, not a parse failure.

session-format.md (Claude Code) and session-format-opencode.md; all three

share the same downstream contract (the internal domain model,

adapter may use the field names below

(.claude/rules/format-isolation.md). The kilocode store is separate

from the other stores (one DB per harness), so nothing here constrains the

other mappings, and vice versa. The shell contract around this mapping — the

harness's default --db name, per-task ingest keys, and extraction version

key — is the harness.md addendum that lands with the CLI wiring, as

opencode's did.

Observed against a real <VSCode globalStorage>/kilocode.kilo-code/tasks/

directory (92 task directories; the shapes below come from six of

Every value in an example position is a synthetic stand-in — no real ids,

Where sessions live

├── ui_messages.json                # the display log (the token source)


├── task_metadata.json              # files_in_context[] only (unread in v1)


└── checkpoints/                    # editor checkpoints (unread)

The two files, and the join between them (the crux)

kilocode splits what other harnesses keep in one place. The conversation

records what the model did but carries no usage at all; the **display

log** carries the usage but no structured conversation. An Assistant

record needs both, so the adapter joins the two files in time order — this

join is the kilocode adapter's crux, the way the message.id repetition

reconciliation is Claude Code's.

api_conversation_history.json — the record spine

An array of {role, content, ts, reasoning_details?} messages; content

is an array of blocks in the observed data (a bare string is tolerated as

text material). The blocks map as follows.

Block Under Mapping
text user message part of the human turn (prompt material)
tool_result user message the tool-result mirror — never a human turn
tool_use assistant message ToolUse{tool: name}
text assistant message display only — no record
reasoning_details (message key) assistant message display only — no record
  • A user message is a HumanTurn when it carries text material (a

string or a text block) — including the observed case of a user message

carrying text alongside a tool_result. A tool_result-only user message

is the Anthropic-format mirror of a tool result and must not delimit

spans.

  • ts orders the file; there is no message id.

ui_messages.json — the token source of record

An array of {ts, type: say|ask, say?/ask?, text, partial?} display rows,

of which the adapter reads exactly one kind.

  • say=api_req_started — its text is a JSON string payload

`{apiProtocol, tokensIn, tokensOut, cacheWrites, cacheReads, cost,

usageMissing, inferenceProvider}. Sampled rows carry usageMissing=false`

with real tokens; the exception is a request that failed or never

completed, which stays usageMissing=true with no tokens.

Everything else — say=text / reasoning / command_output /

checkpoint_saved / user_feedback, and the ask=tool / command /

command_output / followup / resume_task / completion_result rows —

is display or interaction furniture, unread in v1 (ask=tool is the

approval point; the signals table explains why it is still not a usage

signal).

The time-ordered join

An api_req_started row's ts sorts before its request's output (the

usage payload describes the request that follows it in time), so the

adapter walks the merged ts order of both files.

  • Each api_req_started row claims the assistant conversation messages

strictly between it and the next row — its *request window*.

  • One window can hold more than one assistant message (observed: pairs

6–30 s apart, each carrying a tool_use block). The join pairs the row

with the whole window, never a single message.

  • The row yields **one Assistant record** — never one per assistant

message, so there is no repetition to reconcile (the Claude Code

message.id problem does not exist here either)

  • prompt_size = tokensIn + cacheReads + cacheWrites (a documented

assumption, below)

  • out_tokens = tokensOut
  • model = "unknown" — the payload carries no model name

(inferenceProvider is a provider, never a model; mapping one to the

other would be a guess). The reporting-honesty label for this missing

model is a cli.md addendum, alongside sub_tokens_estimated

  • The record is stamped with the window's last assistant message ts —

the request's completion point — so the cost record sits *after* its

window's tool records instead of inverting the stream (the same lesson

the opencode adapter recorded about creation-time stamping). A window

holding no assistant message stamps the row's own ts: that row is a

failed or cancelled request (usageMissing=true, zero tokens) — the

request still happened, and it is recorded with zeros, as the opencode

adapter records an errored request.

  • Assistant messages outside any window (before the first row) carry no

cost record — no measured request row, never fabricated.

Record order within a session is ts order; within a window the tool

records come before that window's Assistant cost record, mirroring the

opencode adapter's ordering.

Config Format Specification

This spec catalogues what the adapter layer knows about Claude Code **config

files** ― the catalog half of the catalog×usage model (architecture.md). Its

sibling session-format.md covers the usage half. Reading config answers *what

is installed and what does it cost to have installed*; the transcript answers

*what was actually used*. Only the adapter uses the paths and shapes below

(.claude/rules/format-isolation.md). Like session-format.md, this is a spec

that tracks an upstream format and will drift.

Observed against a real ~/.claude/ tree on 2026-06-14, Claude Code 2.1.x.

Where config lives

Config exists at two scopes; project overrides/extends global. The adapter scans

both and records the scope on each surface ― Scope::Project carries the

owning project's normalized slug, since many projects coexist in one catalog

(storage.md). Which project roots get scanned is driven by the *sessions*:

analyze collects the distinct real session roots (session-format.md, the

records' cwd, worktree folded onto the parent checkout) and hands them to the

one traversal, catalog_surfaces(harness, roots) (adapter::harness), which

builds each scope, owns the symlink-dedup set, and skips a root that was deleted

since its sessions ran. What a harness scans is its site rows ― a path plus

a loader (Site, listed per harness as global_sites / project_sites) ― so a

new surface kind is a row and a loader, never an edit to that traversal;

read_project_surfaces in adapter/config.rs remains the direct single-root

entry point the tests drive.

~/.claude throughout this document means $CLAUDE_CONFIG_DIR when that

variable names a non-empty path, because Claude Code relocates the whole tree

under it (claude_config_dir in adapter/config.rs); an empty value is

treated as unset.

Surface kind Global Project-local
skill ~/.claude/skills/<name>/SKILL.md (+ plugin skills) <project>/.claude/skills/<name>/SKILL.md
rule ~/.claude/rules/**/*.md <project>/.claude/rules/**/*.md
agent ~/.claude/agents/<name>.md <project>/.claude/agents/<name>.md
claude_md ~/.claude/CLAUDE.md <project>/CLAUDE.md, AGENTS.md, nested
hook, permission ~/.claude/settings.json <project>/.claude/settings.json, settings.local.json
mcp_server ~/.claude/mcp.json (top-level mcpServers) <project>/.mcp.json
mcp_tool the MCP server's advertised tool schemas (dynamic ― see below) ―

CLAUDE.md and AGENTS.md are two names for the same always-on context, and a

repo serving both agent conventions typically ships AGENTS.md as a symlink to

CLAUDE.md. Claude Code injects that content once, so the adapter weighs the

file once: read_claude_md_surfaces resolves each candidate and keeps the first

surface per resolved file, which reports the pair under CLAUDE.md. The

deduplication key is the resolved path, not the content ― two independently

maintained files are two real always-on surfaces even when their text coincides.

Getting this wrong doubles the project's startup_full total, which is what the

always-on floor is reconciled against (surfaces.md).

A CLAUDE.md can pull other files in with @path imports, and Claude Code

injects the imported text every session just like the file's own. Weighing only

the importing file would book a config made of import lines as nearly free and

push the real always-on cost into the unattributed residual ― exactly inverting

the "always-on heavy" wedge for such a layout. So read_claude_md_surfaces

follows the imports and records **each imported file as its own claude_md

surface** (startup_full, id @<path>, relative to the importing top-level

file's directory when inside it), rather than folding the text into the

importer: the cost lands on the file that carries it, and each one can be pruned

on its own. The import rules mirror Claude Code's documented behavior: an import

is an @ opening a whitespace-separated word (an e-mail address is not one),

ignored inside code spans and fenced blocks; it resolves relative to the

importing file, ~/ to the home directory, or as an absolute path; recursion

stops after five hops; an import naming no readable file is skipped. Every

import is further confined to the importing top-level file's directory: a

target canonicalizing outside it (.. escapes, absolute paths, ~/, symlink

hops) is skipped with a warning, so a cloned repo cannot pull host files

outside its root into the catalog. The same

resolved-path deduplication as the AGENTS.md symlink applies across the whole

import graph ― a file imported twice, imported in a cycle, or imported *and*

read as a top-level AGENTS.md is weighed once, with the top-level name

winning.

settings.json carries two surface kinds at once: permissions (allow/deny) and

hooks (matcher → command); the adapter splits one file into several surfaces.

Each hook entry becomes a hook surface named Event:Matcher (bare event when

no matcher is declared) ― the same name the transcript stamps on a firing

(hookName), so firings join their surface. Firing is measured per window;

a hook with no firings reads unused, which is exactly the dead-hook signal

(docs/specs/surfaces.md).

MCP servers are not in settings.json ― they live in a separate mcp.json

(verified: ~/.claude/settings.json has no mcpServers key; ~/.claude/mcp.json

holds them). If a future Claude Code version also accepts inline mcpServers in

settings.json, the adapter reads both ― but mcp.json is the source of record.

Static cost

A surface's static cost is the token weight of the text it injects into the

model's context. It is computed by the adapter from the file content; it is an

approximation (a ranking signal, not a billing figure ― architecture.md),

so a tokenizer that is *close* and *consistent* is sufficient. The exact

tokenizer is a tuning choice (see open question) injected into the weighing

function, not hard-wired.

A surface is weighed twice, because one number cannot answer both questions

a reader has. static_tokens is the whole definition ― for a skill or agent,

what its body costs *when invoked*. startup_tokens is the part every session

pays for merely having it installed: the whole text for an always-on file, the

frontmatter description alone for a skill or agent, nothing for a body that

waits (a path-conditional rule), and *unknown* for an MCP server. Only the second

is what deleting the surface reclaims, and reporting the first as if it were the

saving is a promise the deletion cannot keep (surfaces.md, "Ranking by what

removal actually saves"). Only the description text is weighed for the startup

half ― the listing scaffolding Claude Code wraps it in is upstream's, not the

config's, so counting it would be inventing a figure.

Static cost is a config-side estimate, not a measured runtime component. The

transcript exposes only a *total* prompt size, never a per-surface breakdown

(session-format.md), so static_tokens is never validated, on its own, as the

exact number of tokens that surface contributes at runtime. Two things are

therefore inherently uncertain and must not be presented as fact: the tool's

tokenizer differs from Claude Code's, and whether the text is actually injected

(and when) depends on load_mode, which is itself an assumption (below). The one

honest empirical check the tool *can* make is reconciliation against observed

context ― see surfaces.md "always-on reconciliation". Reports present

static_tokens as an estimate, labelled as such.

Load mode is an assumption table, versioned against the release

load_mode is not read from anything ― it is the adapter's model of how

Claude Code loads each surface kind, maintained as a table pinned to the observed

release (2.1.x). It drives the most consequential wedge ("always-on heavy") and

its suggested moves, so when the table is wrong every wedge built on it is wrong.

It belongs in the "will drift" caveat alongside field names: a release that, say,

lazy-loads CLAUDE.md invalidates the startup_full assumption silently. The

stored enum uses underscores (startup_full, path_conditional, …); the prose

labels below use hyphens for readability ― same values.

What counts as "the injected text" differs by surface and is the crucial

distinction for optimization, because always-on cost is the expensive kind:

Load mode Surfaces Cost character
startup-full CLAUDE.md / AGENTS.md, memory index Paid every session, unconditionally. The heaviest tax.
startup-description skill, agent Only the frontmatter description is loaded at startup; the body is on-demand. Cheap to keep, unless many accumulate.
path-conditional rule with paths: frontmatter Loaded only when a matching file is in play; full body when it fires.
on-demand skill / agent body, when invoked Paid per use ― this is what events measures at runtime.
tool-schema mcp_tool, built-in tools The tool definition injected into the system/tool context. MCP schemas can be very large (the deferred-tool catalog).

So a surface records its full static cost (whole definition), its

startup cost (the slice of that text the load mode actually injects at

session start, per the table above), and its load mode, and the report

distinguishes "always-on" tax from "per-use" cost. A skill whose body is huge but

is invoked daily is a *body-trim* candidate; a CLAUDE.md that is huge is an

*always-on* candidate; a rule that never fires is a *delete* candidate.

The MCP tool-schema hard case

mcp_tool static cost is the one surface whose definition is not a file on disk

― the schema is advertised by the running MCP server. Reading it statically

requires either connecting to the server or finding a cached schema. The adapter

treats this as best-effort: when a schema source is available it is weighed like

any other surface; when it is not, the surface is recorded with an unknown

static cost and the report flags it rather than reporting a false zero. The

runtime side is unaffected ― MCP tool_use still shows up in events.

Investigated and found unmeasurable from local data (the honest limit). None

of the would-be sources exist: mcp.json holds only launch config

(command/args), no schema; there is no on-disk cache of advertised tool

definitions (mcp-needs-auth-cache.json is auth state only); the transcript

exposes only the tools that were *used*, so a server's full tool count is unknown

and an *unused* server ― exactly the one worth flagging ― yields no signal at

all. A differential (baseline with vs without a server) is also unavailable

because every project shares the global mcp.json. A "tool count × average

schema size" estimate would therefore be a fabrication for the cases that matter,

so the tool does not invent one. The honest substitutes it does provide:

per-server call frequency (inventory / waste ― a used vs dead-weight

signal), and the residual in overhead (an upper bound on system + built-in

tools + all MCP schemas combined). Isolating one server's cost would need runtime

schema access this tool does not have.

Frontmatter the adapter reads

  • skill: name, description (the startup-loaded text ― its weight *is*

startup_tokens), argument-hint, allowed-tools. Body length feeds the

on-demand cost. The description is read defensively: a plain or quoted scalar,

or a block scalar folded from its indented continuation lines; a skill

declaring none simply costs nothing at startup.

  • rule: paths: (the load condition) and, when present, description:.

Presence of paths: sets the load mode to path-conditional; its absence means

the rule is always loaded. description: is frequently absent on real rules ―

read it defensively, do not rely on it.

  • agent: name, description (weighed like a skill's), tools, model.

Parsing is defensive: unknown frontmatter keys are ignored, missing optional

keys tolerated. A surface the adapter cannot fully parse is still catalogued

(with what it could read) rather than dropped ― an unparseable surface is itself

worth surfacing.

Identity and the join

Each surface has a stable (kind, id) ― e.g. (skill, git-commit),

(mcp_server, playwright), (rule, spec-sync). The same identity is what

events carries in surface_kind / surface_id, so the catalog×usage join

(surfaces.md) is a key match. The adapter is responsible for deriving the same

id from both sides: the skill surface id from the directory/name, and the

matching event id from the invoked skill name in the transcript.

A surface can exist at both global and project scope under one (kind, id). The

catalog stores both rows (keyed with scope), but the join resolves to the

effective surface ― project shadows global, mirroring Claude Code's own

override ― so one event never matches two surface rows. The full contract is in

storage.md "Surface identity, scope, and the effective join".

Config Format Specification — opencode

This spec catalogues what the adapter layer knows about opencode **config

files** — the catalog half for the opencode harness. Its Claude Code sibling

is config-format.md; the join semantics are shared (surfaces.md). Only the

adapter uses the paths and shapes below. Like every upstream-tracking spec,

this one describes what was observed and marks what was not.

Observed against a real ~/.config/opencode/ tree (opencode 1.x). No

project-level .opencode/ directory and no MCP definition were present in

this environment — the project layout and the MCP site below follow the

documented conventions and are marked as such until a live tree confirms

them.

Where config lives

Config exists at two scopes; project overrides/extends global. The adapter

scans both and records the scope on each surface — Scope::Project carries

the owning project's directory, since many projects coexist in one store

(harness.md: project is the session's directory verbatim).

Surface kind Global Project-local
command ~/.config/opencode/command/*.md <project>/.opencode/command/*.md
agent ~/.config/opencode/agent/*.md <project>/.opencode/agent/*.md
claude_md — (unverified; not scanned) <project>/AGENTS.md (+ its @imports)

~/.config throughout means $XDG_CONFIG_HOME when that variable names an

absolute path, else ~/.config — the XDG rule, mirroring how the store

resolution treats XDG_STATE_HOME.

Which project roots get scanned is driven by the *sessions*, exactly as for

Claude Code: analyze collects the distinct session directories and scans

each root that still exists on disk. A deleted root contributes no project

surfaces.

Static cost and load mode

Both surface kinds load like Claude Code skills: only the frontmatter

description is startup-listed, the body waits for invocation. So each

surface records the whole file as static_tokens (its invocation cost) and

the description alone as startup_tokens, under

LoadMode::StartupDescription. The token estimator is the shared

approx_tokens (roughly four characters per token) — a ranking signal, not

a billing figure.

The startup-listing is an assumption, stated here so a wrong table entry

can be found: it was not verified against opencode's prompt construction the

way the Claude Code table was pinned to release 2.1.x. If opencode lists

only names (not descriptions), every startup_tokens here overstates by the

description weight; the overhead reconciliation against the observed

session-start floor is the honest check.

description is read defensively (plain/quoted/block scalars with folded

continuation lines); a file declaring none costs zero at startup. Unknown

frontmatter keys are ignored.

AGENTS.md reuses the shared claude_md weighing (whole text,

StartupFull, @import files as their own surfaces) — opencode reads the

same file the Claude Code adapter weighs, so the cost lands identically.

CLAUDE.md is deliberately not scanned: opencode's documented

instruction file is AGENTS.md, and cataloguing a file the harness never

loads would invent always-on cost.

Identity and the join

  • command surfaces take the file stem as id (review.md → review).

Commands are catalog-only: a human invoking /review leaves no

structural marker in the transcript (user text is prose, and

substring-matching it would misread discussions *about* commands), so no

event can ever join them. The core already treats unknown kinds as

catalog-only (is_usage_measurable lists only measurable kinds), which is

why no core change backs this spec — absence of events is never read as

disuse.

  • agent surfaces take the file stem as id and join agent_spawn events by

the task tool's subagent_type. Built-in agents (build, explore,

…) exercised without a matching file surface appear as orphaned usage,

the mirror of unused config — reported, not hidden.

  • A surface existing at both scopes under one (kind, id) resolves per

project (project shadows global), exactly as for Claude Code.

Deliberately out of v1

  • Skills — catalogued from the six documented sites (docs/skills/):

opencode-native (.opencode/skills/, ~/.config/opencode/skills/) first,

then the compatible homes opencode also loads (.claude/skills/,

.agents/skills/, and their global forms). Sites may reach one shared

directory through symlinks (.opencode/skills -> ../.agents/skills is the

observed shape), so surfaces dedup by canonical path — one row per

actual definition, no matter how many sites reach it. Deduping by name

instead would mark the shared definition unused at one scope (a wedge the

catalog manufactured); deduping by path keeps one honest row joined by

every tool=skill event.

  • MCP servers. No MCP definition was present (opencode.json carries no

mcp key here), and no MCP-namespaced tool appeared in the usage sample,

so the server↔tool join cannot be pinned down. Skipped until both halves

are observed together.

  • **permission surfaces.** The opencode.json permission table is real,

but no runtime denial signal joins it (see session-format-opencode.md),

so every entry would read "unused" — a false wedge manufactured by the

catalog, not found in usage. Skipped until a denial marker is found.

  • **Global AGENTS.md.** Whether opencode loads one is unverified; only the

project file is scanned.
