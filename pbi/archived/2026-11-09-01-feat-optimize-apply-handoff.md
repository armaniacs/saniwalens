# PBI: optimize 適用ハンドオフ (ヘッドレスのプランを対話に渡して適用する)

## ユーザーストーリー
opencode などのヘッドレス harness で saniwalens を使う人として、ヘッドレス `optimize` が出した適用プランをファイルに残し、そのファイルを読み込ませた対話セッションで適用まで進めたい。なぜなら今はプランが出て終わりで、適用が手作業に切り戻されるからだ。

## ビジネス価値
- ヘッドレス harness でも doctor から適用までの動線が一筆書きになり、opencode 利用者の改善サイクルが回る
- プランがファイルに残ることで、適用内容の再現性とレビュー可能性が上がる
- 測定方法: `optimize` 実行から適用セッション起動までの操作が1コマンドで終わること

## 現状確認 (Phase 0 済み)
- キーワード検索 (`apply` / 引き継ぎ等で `src/` と `docs/specs/` を調査) で、ヘッドレス結果を対話に渡す仕組みは存在しないことを確認済み
- 既存コマンド一覧: `analyze` / 各 view / `sql` / `optimize` / `tui`。提案を適用するコマンドは存在しない
- 唯一の関連資産: ヘッドレス実行の生ログファイル (`cli/headless.rs` が成功時に削除、失敗時は残置) と、指示文の書き分け (`core/optimize.rs`: 対話は承認ゲートの後に編集可、ヘッドレスは編集禁止でプラン出力のみ)

## BDD受け入れシナリオ

Scenario: ヘッドレスのプランが保存され対話に渡る
  Given ヘッドレス harness (opencode) で store が用意されている
  When  適用付きの `optimize` を実行する
  Then  プラン本文がファイルに保存される
  And   そのファイルを読み込ませる対話セッションが起動される
  And   対話側の初手プロンプトが保存ファイルの読み込みと適用を指示している

Scenario: 通常実行では何も残さない
  Given ヘッドレス harness で store が用意されている
  When  通常の `optimize` を実行する
  Then  従来どおりプランが出力されるだけで対話セッションは起動しない
  And   プランファイルは作られない

Scenario: ハンドオフ実行では常にファイルが残る
  Given ヘッドレス harness で store が用意されている
  When  ハンドオフ付きの `optimize` を実行する
  Then  選択を問わずプランファイルが残りパスが表示される
  And   掃除は別コマンドに任せることが分かる表示がある

Scenario: 失敗時は秘密を残さずガイドが死なない
  Given 対話バイナリが存在しない環境がある
  When  適用付きの実行で対話起動に失敗する
  Then  エラーが分かる文言で報告される
  And   保存済みプランファイルの扱い (残す/消すとパス) が明示される

## 受け入れ基準

- [x] 保存ファイルは 0600 等の私的権限で作られる (error 抜粋など秘密を含みうるため。既存の briefing 私的 temp と同水準)
- [x] `cargo test` と `cargo clippy --all-targets -- -D warnings` が green
- [x] `docs/specs/cli.md` の `optimize` 節が同一変更で更新されている

## テスト戦略 (t_wadaスタイル)

### E2Eテスト
- 適用なし実行が従来出力を変えないこと (既存 E2E の延長)
- 適用付き実行の実起動はモノのバイナリを叩くため、E2E では起動拒否系 (バイナリ不在など) のみを対象にし、正常起動は対象外とコメントで明記する

### 統合テスト
- プラン本文の抽出 (生ログから JSON イベント行を除く) の入出力テスト
- 保存パスの解決テスト (state home 基準、相対 XDG の無視など既存流儀に従う)

### 単体テスト
- プラン抽出の境界値 (空出力、JSON のみ、本文なし)
- 対話プロンプト文面の組み立て (保存ファイルのパス埋め込み)
- 失敗時の扱い分岐 (起動失敗でもガイド/呼び出し側が死なない)

## 実装アプローチ
- **Outside-In**: 受け入れ (プラン抽出の入出力テストを Red) から開始し、内側へ進む
- **Red-Green-Refactor**: TDDサイクルを各レイヤーで適用
- **リファクタリング**: グリーンになるたびに品質改善

## 見積もり
4 (要チームでの見積もり。内訳目安: プラン抽出 2、保存と権限 1、対話起動 1。opencode TUI 渡し方のスパイクは別PBIに分離済み)

## 技術的考慮事項
- 依存関係: 既存の `deliver` / `DeliveryPlan` シームと `Harness::launch_command` を壊さないこと。新経路は追加で作り、既存の Print / Interactive / Headless の振る舞いを変えない
- テスタビリティ: 子プロセス起動はテスト外に隔離し、文面とパス解決を純粋関数に寄せる
- 非機能要件: プランファイルは秘密を含みうる (0600、私的 temp と同水準、成功時の削除方針を決める)。実 transcripts / 実 config / 生成 DB は決してコミットしない
- opencode TUI へのプロンプト渡し方法は未確認のためスパイク扱い。分からなければ PBI 分割 (調査と実装の分離) を検討する
- 先行作業: 対話起動形状のスパイク (`pbi/2026-11-09-02-spike-opencode-tui-prompt-handoff.md`) を先に実施し、各 harness の渡し口を確定してから本体に着手する。番号は前後するが実施順はスパイクが先

## 実装者向け注記

### 現状コードの確認
(着手前に必ず実行すること)
```bash
grep -rn "Do not edit any files" src/core/optimize.rs
grep -rn "launch_command\|RunMode" src/adapter/harness.rs | head
```

### 実装手順
1. プラン抽出の入出力テストを Red で書く (生ログ相当の合成入力からプラン本文だけが残ること)
2. プラン抽出を実装して Green にする
3. 保存パス解決のテストを Red で書く (state home 基準、0600 作成まで含む)
4. 保存処理を実装して Green にする
5. 対話プロンプト文面のテストを Red で書く (ファイルパス埋め込み)
6. 起動経路を harness ごとに実装し、ガイドの「次の一手を実行」との接続点を決める (起動までか適用完了までか)
7. spec (`docs/specs/cli.md` の `optimize` 節) を同一変更で更新する

### 落とし穴
- ヘッドレスの生ログは JSON イベント行混じりのため、行レンダラ (`run_line_renderer`) の Text だけを拾うのか最終プラン節だけを切り出すのかを先に決める。混ぜるとゴミがプランファイルに入る
- ガイドの StdinLock を握ったまま子プロセスに対話を引き渡すと先読み入力が欠けることがある。ガイド内起動は既存の「次の一手を実行」と同じ注意書きで済ませ、入力方式は変えない
- 既存の `DeliveryMode` に第4の値を足すか追従ステップにするかは実装時に選ぶ。どちらでも既存3モードのテストを壊さないことが条件

### 新たに発見したリスク
- 掃除コマンド到着までの窓の間、秘密を含むプランファイルが蓄積する (0600 で緩和、解消は掃除PBI待ち)
- スパイク結果次第で本体設計が変わる (opencode の渡し口なしなら表示フォールバック。harness 間で体験が割れる可能性)

### 未解決の疑問
- 掃除コマンドの形状 (保持世代数か期限か、コマンド名は何か)。別PBIで決める
- ハンドオフ起動の表現 (専用フラグか `optimize` の追従動作か)。スパイク確定後に実装者が選ぶ

### 決定事項
1. 先行: `02-spike` で各 harness の対話起動形状を確定してから本体に着手する
2. 本体: ハンドオフ実行時は常にプランファイルを残しパスを表示する。通常 `optimize` は従来どおり何も残さない
3. 適用は harness 自身の対話セッションが行い、渡すのはプラン本文＋store 参照
4. ガイド接続と掃除コマンドは別PBIに分離する
