# PBI: `--apply` 系エラーメッセージの正確化

## ユーザーストーリー
対話 harness の利用者として、`--apply` 拒否時や空プラン失敗時に正確な
エラーメッセージを読みたい。なぜなら誤った表示は原因特定を遅らせ、
フォレンジクス時のノイズになるからだ。

## ビジネス価値
- 誤表示の排除2件 (将来の第三 harness 追加時の誤認防止、空プラン失敗時の誤解防止)
- 測定方法: 該当操作時のメッセージが実態と一致すること。既存テストは全件維持

## 現状確認 (Phase 0 済み)
- `src/cli/handoff.rs:41` の `(opencode)` ハードコードを確認済み
- `src/cli/handoff.rs:192` の `(raw log removed)` を確認済み
  (raw ログはメモリ上の `log_text` のみで、削除対象のファイルは存在しない)
- ゲート述語自体は正しい (網羅 `match` + 契約テスト済み)。直すのは文言のみ

## BDD受け入れシナリオ

```gherkin
Scenario: 許可される headless 群が文言と一致する
  Given 対話 harness で --apply を実行した
  When  拒否メッセージを読む
  Then  実際に許可される harness 群と矛盾しない表示である

Scenario: 空プラン失敗の後始末表示が正確である
  Given 空の headless 出力で --apply が失敗した
  When  エラーメッセージを読む
  Then  削除されたことになっていないものは削除済みと書かれていない
```

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- 不要 (文言のみの変更。既存の拒否系テストが回帰網になる)

### 統合テスト
- 拒否メッセージの内容テスト (許可 harness 群との一致。生成方式にした場合のみ)

### 単体テスト
- 文言定数のテスト (ハードコードを残す場合の更新漏れ検出用。方式次第で省略可)

## 技術的考慮事項
- 依存関係: ゲート述語 (`require_headless_mode`) には触れない。文言層のみ

## 実装者向け注記

### 現状コードの確認
（着手前に必ず実行すること）
```bash
# 対象文言の位置
grep -n "headless harness (opencode)\|raw log removed" src/cli/handoff.rs
# 文言を固定しているテスト
grep -rn "headless\|raw log\|no plan file" src/cli/handoff.rs tests/ | grep -i "test\|assert" | head -n 20
```

### 実装手順
1. 既存テストを Red 化できるか確認する (文言を仮変更して落ちること)
2. 拒否メッセージを修正する (生成またはコメントのいずれか)
3. 空プラン文言を修正する (削除対象の実態に合わせる)
4. 全テストを Green にする (固定側の同時更新を含む)

### 落とし穴
- 文言変更が help golden や他テストの固定に波及しないか確認すること
- ゲート述語の振る舞いは変えない (文言層に留めること)
- 実 transcripts / 実 config をテストに使わない。fixture は合成のみ
