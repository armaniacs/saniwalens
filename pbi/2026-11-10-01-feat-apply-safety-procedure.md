# PBI: 適用手順の安全規格 (バックアップ・diff・確認・適用・結果)

## ユーザーストーリー
saniwalens の提案を適用する人として、適用前にバックアップが取られ、修正前後の diff が示され、確認して OK したら適用され、結果が分かるようになっていてほしい。なぜなら承認なしの直接編集は怖く、適用されたか提案だけかも分からないからだ。

## ビジネス価値
- 適用への信頼 (壊しても戻せる) がないと optimize の提案は実行に移せない
- 適用結果サマリで「実施されたのか提案だけか」が一目で分かる
- 測定方法: 適用セッションの出力にバックアップ場所・diff・承認記録・結果一覧が残ること

## 背景 (なぜなぜ分析 2026-11-10 より)
- ガイド内実行の直後に harness 保存の問いが出て「何を保存するのか」が曖昧になった (別対応 A)
- ヘッドレス出力に適用状態の宣言がなく P1/P2/P3 が実施済みか不明だった (別対応 B)
- 本 PBI はその先: 適用する側の手順規格がそもそも存在しないことが根本原因だった

## BDD受け入れシナリオ

Scenario: 適用はバックアップ・diff・確認を経る
  Given 適用対象のプランと編集対象ファイルがある
  When  対話適用セッションが編集に入る
  Then  編集前にバックアップが取られている
  And   修正前後の diff が提示されている
  And   明示的な承認の後でのみファイルが変更されている

Scenario: 適用結果が分かる
  Given 適用セッションが終わっている
  When  出力を読む
  Then  変更されたファイルの一覧と各々の要旨が残っている
  And   提案のみで終わった項目と適用した項目が区別できる

Scenario: 承認がなければ何も変わらない
  Given diff が提示されている
  When  承認しないと答える
  Then  ファイルは変更されていない
  And   バックアップの扱い (残す/消すとパス) が分かる

## 受け入れ基準
- [ ] `apply_prompt` (対話適用の指示文) に手順が規定されている (バックアップ→diff提示→承認→適用→結果サマリ)
- [ ] バックアップ方式が決まっている (git 管理下とそうでない場合の両方。 Verhandlungen 可だが両対応か片方＋明示が必要)
- [ ] 結果サマリの形式が決まっている (変更ファイル一覧＋要旨＋提案のみ項目の区別)
- [ ] 既存の承認ゲートと矛盾しない (承認は1回だけが原則。diff 確認と適用承認を分けたい場合は明示する)
- [ ] `cargo test` と `cargo clippy --all-targets -- -D warnings` が green
- [ ] `docs/specs/cli.md` の該当節が同一変更で更新されている

## テスト戦略 (t_wadaスタイル)

### E2Eテスト
- 実バイナリ起動の正常系は対象外としコメントで明示する (既存の流儀どおり)

### 統合テスト
- 指示文の組み立てテスト (バックアップ手順・diff 提示・承認・結果サマリの各節が含まれること)

### 単体テスト
- 文面の境界値 (対象ファイルなし、承認なし分岐の文言)
- 既存の承認ゲート文言との重複・矛盾がないこと

## 見積もり
3 (要チームでの見積もり。内訳目安: 指示文 1、テスト 1、spec＋確認 1)

## 技術的考慮事項
- 依存関係: `--apply` ハンドオフ (`feature/optimize-apply-handoff` 作業ツリー) の対話適用経路が前提。ブランチ上で実装すること
- テスタビリティ: 指示文は純粋関数に寄せ、起動経路のテストと分離する
- 非機能要件: バックアップは秘密を含みうるため私的権限。バックアップの保管場所と寿命を決めること
- 前提: ヘッドレス側の「提案のみ」宣言は別対応 B で入る。本 PBI は対話適用側のみ

## 実装者向け注記

### 現状コードの確認
```bash
grep -rn "apply_prompt\|approval\|承認" src/core/optimize.rs | head
grep -rn "ask_yes_no\|保存しますか" src/cli/views/guide.rs | head
```

### 実装手順
1. `apply_prompt` の現行文面テストを Red で書く (手順4節の存在確認)
2. 指示文にバックアップ→diff→承認→適用→結果サマリを追記して Green にする
3. 結果サマリ形式のテストを追加する (変更/提案のみの区別)
4. spec を同一変更で更新する

### 落とし穴
- 既存の「承認は1回だけ」原則と diff 確認をどう数えるかを曖昧にしない。2回聞くならそう書く
- git 管理外のファイルのバックアップ方式を未定義にしない (`.bak` 方式など代替を明示)
- 実 transcripts / 実 config をテストに使わない。fixture は合成のみ
