# PBI: flaky test 検出の仕組みを用意する

## ユーザーストーリー
開発者・メンテナとして、テストスイートを繰り返し実行して不安定テストを洗い出すスクリプトまたは CI ジョブがほしい、なぜなら偶発的な赤の原因を先に特定できるからだ。

## 優先度
- 順位: 25 / 全28件
- RICEスコア: 2.0（Reach=1 / Impact=1 / Confidence=2 / Effort=1日）
- 根拠: 現状 391 tests、CI は 1 回実行で flaky は発見できない。スクリプトにするか CI ジョブにするかは discovery で決めてよい

## BDD受け入れシナリオ
Scenario: 繰り返し実行で不安定テストが報告される
  Given 同一のテストスイートを複数回繰り返し実行する仕組みが用意してある
  When  同一テスト群を N 回実行する
  Then  一度でも失敗したテストの名前が、失敗した回数つきで報告される

Scenario: 不安定テストが無ければ green で終わる
  Given N 回の繰り返し実行で失敗が一度も無い
  When  検出の実行が終わる
  Then  失敗ゼロの報告を出して green で終了する

## 受け入れ基準
- [x] 同一テスト群を N 回（既定5回）実行し、一度でも失敗したテスト名が回数つきで報告される（scripts/flaky_repeat.sh。bash3.2互換）
- [x] 失敗が一度も無ければ green で終わる（N=1で実行確認）
- [x] 報告に、疑わしい非決定性の切り口（時計・乱数・並列実行依存）を確認する指針が付く（スクリプト末尾に出力）
- [x] CI ジョブとして追加する場合（追加しない決定。オンデマンド実行のみ。トークン不要）、token や秘密情報が無くても green で実行できる（gate は secrets でなく vars に置く）
- [x] 既存の検証（cargo fmt --check、cargo clippy（Rustコード不変。スクリプトのみ） --all-targets --all-features -- -D warnings、cargo test）を壊さない
- [x] 検出自体が決定的で、実行のたびに結果の解釈が変わらない（同一出力→同一集計の純粋パース）

## テスト戦略
- E2E: スクリプトまたは CI ジョブの実行結果が報告形式どおりになる（不安定テストあり / なしの両ケース）
- 統合: cargo test の実行結果（成功・失敗・出力）を繰り返し実行で集計できる
- 単体: 既知の失敗出力から失敗テスト名を抽出して集計する解析

## 実装者向け注記
- 現状の確認（2026-10-31）: CI（.github/workflows/ci.yml）の test ジョブは ubuntu の 1 回実行のみ（nix develop -c just test）。flaky を洗い出す仕組みは無い
- 時計や乱数・並列実行依存を疑う対象は tests の非決定性。core は純粋で I/O フリー（.claude/rules/tdd.md）なので、非決定性は I/O 側（temp dir 名・並行テスト・環境変数の読み書き）に寄る
- CI 追加の場合は token 無しでも green にする（#9 / #10 の教訓。cachix-action の gate が vars.CACHIX_ENABLED に置かれている例は ci.yml を参照。secrets ベースの if にするとワークフロー自体が評価されなくなる）
- N 回実行は cargo test を単純にループして試行ごとの失敗テスト名を集計する形で足りる。並列ジョブにしない（結果の解釈が複雑になる）
- spec 更新: コードの動作変更が無い（スクリプト / CI 追加のみ）場合は spec 更新は不要。CI に組み込む場合はその挙動を docs に記す
