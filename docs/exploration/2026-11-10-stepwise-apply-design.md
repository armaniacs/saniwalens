# 段階適用ウォークスルー設計 — 提案項目単位の予定diff承認

- 日付: 2026-11-10
- 起点: ガイド内 `optimize` 実実行の観察 (2026-11-09)。ヘッドレス出力に「提案のみ」宣言は入ったが、
  適用側は単一承認ゲートのままで、項目ごとの確認ができない
- 前提: `--apply` ハンドオフ (`feature/optimize-apply-handoff` 作業ツリー) と
  適用手順の安全規格 (PBI `pbi/2026-11-10-01-feat-apply-safety-procedure.md`) の上積み

## 決定事項 (brainstorming より)

- ステップの単位: 提案項目単位 (P1-a・P1-b…の1項目＝1ステップ)
- diff の時期: 適用前の予定diff (`diff -u` 形式)。承認までファイルは無変更
- 選択肢: `y` 適用する / `n` 飛ばして次へ / `q` 全体を打ち切る
- 駆動方式: 指示文駆動・厳密ステージ (A案)。`apply_prompt` に手順を規定し、文面テストでピン止めする

## §1 1項目の進行 (厳密ステージ)

各項目でこの順序を必須化し、選択なしに次へ進むことを禁止する。

1. 対象ファイルの現状を読み、変更前にバックアップする (既定の `backups/` 流儀を踏襲)
2. 予定diffを提示する (未適用の old→new、`diff -u` 形式)
3. 解説する (なぜこの変更か・何が直るか・リスクは何かを短く)
4. 選択を聞く (`y`/`n`/`q`)
5. `y` のときだけ適用し、適用後に実diffの一行サマリを残す

## §2 終了条件

- `q` で打ち切った場合、未処理項目の一覧と「残りは未適用」の宣言で終わる
- 全項目の選択が出たら、適用済みとスキップの一覧サマリで終わる
- 「残り全部やって」のような包括指示が来ても、未選択の項目を黙って適用しない (§1の禁止を優先する)

## §3 既存設計との関係 (変更点)

- 適用手順の安全規格の「承認は1回だけ」原則は項目別承認に更新する。全体の一括承認はなくす
- ヘッドレス側の「提案のみ宣言」は不変
- 対話側の結果サマリ形式 (`## Applied changes` / `## Proposal only (not applied)`) は流用する。
  スキップ項目は後者の under に記載し、行き先を明確化する

## §4 テスト・spec

- 指示文の純粋関数テスト: §1の5手順の存在と順序、`y/n/q` の定義、包括指示の拒否文言をピン止めする
- spec は `docs/specs/cli.md` の `--apply` 段落を同一変更で更新する (新規節なし)
- E2E の実起動は対象外とし、コメントで明記する (既存流儀)

## 非目標

- 機械検証ゲート (CLI側の遵守検査) は将来の堅牢化枠とし、本設計に含めない
- CLI駆動ウィザード化 (項目の機械切り出し) はしない
- ガイド接続・掃除コマンドは別PBIのまま
